Problem
The legacy implementation is not dead, it is a zombie: a Settings save of HATCHDOOR_EXCLUDE or HATCHDOOR_EMBED_LAYERS rebuilds the startup VAULT_PATH into tables no read uses, a HATCHDOOR_GIT_* save answers 503 until that rebuild has run, and modern MCP tools.listChanged honesty rests on a signal only the legacy rebuild sends.
Solution
Delete the lane; point the three surviving callers (settings reindex, Git settings, marker-set change) at the collection lane's coordinator and per-Vault definitions, and drop VAULT_PATH as a Vault source.
Deletion test
Nothing reappears. The collection lane already answers every product question the legacy lane did. The strongest possible yes.
Wins
  • Locality: one indexing path, one Git path
  • AppState 25 → 15 fields
  • Every test fixture stops calling build_cache
  • Settings saves act on the Vault collection
  • listChanged fed by the real Index turn
  • Module map sheds its stale entries
ADR-10 describes the mechanism this lane implements (debounced background commit-and-push). The managed per-Vault Git turn superseded it in practice without a record. Worth reopening: ship a superseding ADR alongside the deletion so the "writes do not block on sync" invariant is restated for the collection lane.
Unlocked after this card
SpeculativeOne cache table family. Every Index turn builds through the legacy notes/chunks schema in a candidate cache and transcribes into vault_* (vault_snapshots.rs:141–188). Once the legacy tables have no other writer the candidate schema can be the vault_* schema. ADR-15: needs eval numbers even if retrieval is nominally unchanged.
SpeculativeFold git/sync.rs into managed_sync.rs. managed_sync.rs re-implements stage_vault_drift and merge_remote with a different error type and imports nothing from sync.rs. After the lane goes, ~250 live lines remain in sync.rs. Needs the ADR-10 successor first.

Problem

Problem
All 9 read tools and 7 management tools build axum extractors, call a handler, read the Response body back through a byte cap and two serde passes; zero tools call VaultReadCore or VaultSearchCore. Testing one tool means the full transport on both sides (all 84 tests in mcp/routes.rs).
Solution
Tools call the read and search cores directly, and results.rs types are the projection types, so "handler drift fails loudly" becomes "there is one type".
Deletion test
Deleting the proxy concentrates nothing: the cores already own the logic. The proxy is pass-through plus a schema check that belongs on the type.
Wins
  • Tool tests need no HTTP framing
  • Interface is the test surface: the core
  • One serialisation instead of three
  • Demo surface gating reaches attachment tools
ADR-17 / ADR-02. ADR-17 wants the tool catalogue framework-independent; this removes its dependence on axum. ADR-02's "one shared core" is today satisfied by routing MCP through the HTTP adapter rather than the core.

Solution

Top recommendation

1. Retire the legacy single-Vault lane

It is the only candidate that fixes wrong behaviour today (a Settings reindex that rebuilds the wrong index, Git settings that answer 503, a listChanged signal with a dead sender), and it clears the ground for everything else: every later candidate's tests inherit the fixtures and the 25-field AppState this deletion halves.
