# Phase 1.6 — Outcome: Hybrid Retrieval Beats Neural Reranking

> Status: decision record. Captures the conclusion of the Phase 1.6 eval. Supersedes the deployment direction implied by `2026-05-19-phase-1.6-reranker-design.md` (which planned to add a cross-encoder reranker to production). Cross-encoder reranking remains in the codebase as an offline-eval reference only.

## TL;DR

We evaluated two cross-encoder rerankers against the existing 26-query eval set on the production-target VM (7 QEMU vCPUs, no real AVX) and against a hybrid-retrieval baseline (Nomic embedding + SQLite FTS5 BM25, fused with Reciprocal Rank Fusion). Hybrid retrieval won on every metric **and** ran ~27× faster than the smallest viable cross-encoder. **The neural reranker is dropped from the runtime path.** Hybrid is what ships in Phase 2.

## What we measured

Same 26 queries, same cache, same metrics (Recall@5/10, MRR, FP-rate@5):

| | R@5 any | R@5 all | R@10 any | R@10 all | MRR | FP@5 | Median e2e |
|---|---|---|---|---|---|---|---|
| Nomic + JINARerankerV1TurboEn (k=10) | 0.962 | 0.949 | 1.000 | 0.968 | 0.878 | 0.750 | 5198 ms |
| Nomic + JINARerankerV2BaseMultilingual (k=20) | — | — | — | — | — | — | ≥45 min budget; never finished on this hardware in interactive testing |
| **Hybrid (Nomic + FTS5 BM25, RRF k=60, initial-k=20)** | **1.000** | **0.968** | **1.000** | **0.978** | **0.894** | **0.500** | **194 ms** |

(Full per-run rows live in `eval/results.md`.)

## Why hybrid was the right answer here

1. **Hardware constraint is permanent.** The deployment target is a 7-vCPU QEMU VM with no real AVX. Cross-encoder inference on a 30M-param distilled model already costs ~5 seconds per query at k=10. A 278M-param multilingual model is multiple minutes per query. Neither is reversible — we cannot upgrade the CPU and cannot increase vCPU count. Any design that relies on a neural reranker at runtime is dead on arrival here, regardless of quality.

2. **Hybrid retrieval is essentially free.** FTS5 BM25 is built into SQLite and already populated (`note_fts` virtual table). Vector search is already running. The only added work per query is one FTS lookup, a hashmap RRF fuse, and a sort — microseconds. The 194 ms median latency is dominated by the Nomic query embedding itself, which is required for any semantic path.

3. **Hybrid was also higher quality on this eval.** Not just "good enough" — it beat the cross-encoder on every metric, including the metric Phase 1.6 was created to fix. FP-rate@5 was the original motivation for adding a reranker (Nomic alone leaked anti-expected near-duplicates); hybrid drops FP-rate@5 from V1 Turbo's 0.750 down to 0.500, while V2 Multilingual was never runnable to confirm its number. Lexical BM25 punishes the near-duplicate antis that pure embedding promotes, because the antis share *embedding-space* surface vocabulary with the query but not the *lexically distinctive* terms.

4. **Phase boundary was the wrong frame.** Phase 2 is the planned home for hybrid retrieval at runtime, so it was tempting to defer this decision. The eval would have been meaningless deferred: if no neural reranker can ever ship on this hardware, evaluating *which* neural reranker is best is pointless. The eval's only legitimate purpose is to answer "what should we ship?" — and that question forced the comparison against hybrid.

## What this changes about Phase 2

- Default retrieval path = hybrid (semantic + FTS5 BM25 via RRF). No cross-encoder in the live MCP/search flow.
- Cross-encoder code (`src/rerank/`, `src/eval/rerank_runner.rs`, `eval rerank` subcommand) stays in tree as an **offline quality-ceiling reference** — useful for benchmarking future approaches, not for production.
- Phase 2 spec should adopt the hybrid retriever as a first-class component, not as an optimization on top of pure semantic search.

## Caveats worth remembering

- The eval set is **26 queries against 490 chunks**. The result is strong but the corpus is small. If the vault grows by ~10×, re-run `eval hybrid` and `eval run` to confirm hybrid still wins. Quality gaps can shrink at scale (more chunks = more chances for FTS to mis-rank).
- FTS5 here is at **note** granularity (`note_fts`), while semantic search is at **chunk** granularity. We collapse semantic-chunk hits to notes by "best chunk per note wins" before fusion. A long note where the query term appears in an unrelated section can lift the whole note. If/when that becomes a measurable problem, a chunk-level FTS index is the fix — but it's a schema add, properly Phase 2 design work.
- RRF k=60 is the published default and was not tuned. The eval did not sweep this — there is likely some lift available from tuning, but no reason to do it before Phase 2 implementation.
