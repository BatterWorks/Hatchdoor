# Phase 1.5 — Evaluation Harness Design

> Status: design approved through brainstorming. Implementation plan to be drafted next via `writing-plans`.

## 1. Goal

A repo-local developer tool that runs a labelled query set against `SqliteCache::semantic_search` under different embedders, scores results with retrieval metrics, and produces a versioned report. The harness exists to drive the embedding-model swap decision and to catch regressions in future tuning work. No production API surface.

## 2. Comparison set

Three best-in-tier models among fastembed 4.9.1's `EmbeddingModel` enum:

| Model | Params | Dim | Context | Role |
|---|---|---|---|---|
| `BGESmallENV15` | 33M | 384 | 512 tok | Baseline (current production model) |
| `NomicEmbedTextV15` | 137M | 768 (Matryoshka 64–768) | 8192 tok | Best small/mid alternative |
| `MxbaiEmbedLargeV1` | 335M | 1024 | 512 tok | Best large |

Chunker, pre-embed normalization, and chunk boundaries are identical across all three runs. The eval isolates the embedder, nothing else.

The original spec's Arctic-S / Arctic-M candidates are dropped: neither is exposed by fastembed 4.9.1's `EmbeddingModel` enum, and the existing code already loads `BGESmallENV15` despite being named `ArcticEmbedder` (see §9).

## 3. Query set

### 3.1 Location and format

- **Path:** `eval/queries.jsonl`.
- **Format:** JSON Lines. One query per line. Parsed in Rust with `serde_json`.
- **Drafting:** queries are first authored as the markdown scratchpad at `docs/superpowers/specs/2026-05-18-phase-1.5-eval-draft-queries.md`, then converted to JSONL once authoring stabilizes. The scratchpad is not the eval input; the JSONL is.

### 3.2 Per-query schema

```json
{
  "id": "U1",
  "query": "Where does my Plex media live?",
  "expected_notes": ["Homelab Atlas", "Host — BatterVision (VM 112)", "Homelab Storage — MergerFS & SnapRAID Runbook"],
  "expected_heading_path": null,
  "anti_expected": []
}
```

- `id` — short stable identifier (`U1`, `U2`, … for user-authored; `D1`–`D20` for drafted).
- `query` — the natural-language query string passed to `semantic_search`.
- `expected_notes` — list of one or more note slugs (filename without `.md`) that should appear in top-k. Multi-note labels are supported natively.
- `expected_heading_path` — optional. Heading path within the (single) expected note where the answer sits. Unused by the v1 metrics; recorded for future chunk-level grading.
- `anti_expected` — optional list of note slugs that should *not* appear in top-k. Only used on queries where surface-vocabulary distractors exist; not every query needs them.

### 3.3 Initial size

~26 queries (20 drafted + 6 user-authored, see the scratchpad). The set grows on demand: when real use surfaces a query that returned junk, that query is added. The eval does not aim for statistical airtightness; it aims to be directionally trustworthy for choosing between three concrete models.

## 4. Metrics

Computed per model:

| Metric | Definition |
|---|---|
| Recall@5 (any-hit) | Fraction of queries with ≥1 expected note in top-5. |
| Recall@5 (all-hit) | Mean of `|expected ∩ top-5| / |expected|` across queries. |
| Recall@10 (any-hit) | As above, k=10. |
| Recall@10 (all-hit) | As above, k=10. |
| MRR | Mean reciprocal rank of the first expected note across queries. Queries with no expected note in top-10 contribute 0. |
| FP-rate@5 | Fraction of queries where any `anti_expected` note appears in top-5. Lower is better. Only queries with non-empty `anti_expected` count toward the denominator. |

NDCG is dropped: there are no graded relevance labels at this scale.

## 5. Harness shape

A single binary at `src/bin/eval.rs` with two subcommands. Eval code never ships in the production `hatchdoor` binary.

### 5.1 `eval build`

```
cargo run --release --bin eval -- build --model <model-id> --cache <path>
```

- Loads the chosen embedder.
- Creates a fresh SQLite file at `<path>` with the `vec0` virtual table dimensioned to match the model (384 / 768 / 1024).
- Indexes the entire vault (parse → chunk → embed → insert), using the same indexing pipeline the production binary uses on cold start.
- Stamps the model identifier and the wall-clock build duration into a `meta` table inside the cache so `eval run` can detect mismatch and so the markdown report can quote build time without re-measuring.
- Logs per-note progress to stdout (already implemented in the indexing layer per commit `6f649d5`).
- Reports wall-clock build time at the end.

### 5.2 `eval run`

```
cargo run --release --bin eval -- run --cache <path> --model <model-id> --queries eval/queries.jsonl
```

- Verifies that the cache's stamped model ID matches `--model`; refuses with a clear error if not.
- Loads the embedder.
- For each query: embeds with `embedder`, calls `SqliteCache::semantic_search(embedder, query, 10)`, computes the metrics.
- Prints a compact terminal table.
- Appends a section to `eval/results.md` with timestamp, model, build time (if known), aggregate metrics, and per-query breakdown.

### 5.3 Three-cache workflow

The three caches live side-by-side:

```
data/cache/hatchdoor-cache-bge-small.sqlite3
data/cache/hatchdoor-cache-nomic-v1-5.sqlite3
data/cache/hatchdoor-cache-mxbai-large.sqlite3
```

(The production binary continues to read its own configured cache at `data/cache/hatchdoor-cache.sqlite3`. The eval caches are independent.)

Build all three once, then compare freely. A model swap in production is later applied by changing the production binary's `Embedder` and pointing it at one of the pre-built caches (or rebuilding the production cache fresh).

### 5.4 Long-running builds

The mxbai-large build is expected to take roughly an hour on CPU; Nomic v1.5 around 20–30 minutes; BGE-small ~10 minutes. Two implications the implementation must respect:

- **No artificial timeouts.** The harness does not impose a watchdog on the build phase.
- **Continuous progress output.** The build streams per-note progress to stdout the whole way through, so a long build is observably alive. The build is normally run in the foreground from a terminal that can stay open (or via `tmux`/`nohup` for very long runs). Resumable builds are not in scope; if a build fails partway, the partial cache file is deleted and the build is restarted.

The README for `eval/` will document this and recommend running the large-model build overnight or unattended.

## 6. Output

### 6.1 Terminal

A single table printed at the end of `eval run`, columns `metric`, `value`, plus a one-line summary identifying the run.

### 6.2 `eval/results.md` (committed to git)

The durable audit trail. Each `eval run` *appends* a new section. Sections are not deduplicated or overwritten — re-running the same model on the same query set produces a new section, which is fine; the file becomes the chronological record of how the system performed at different points in time.

Each section contains:

- Header with timestamp, model ID, build time (looked up from the cache's meta table), query-set commit SHA or path.
- Aggregate metrics table from §4.
- Per-query breakdown table: `id`, `query` (truncated), `rank of first expected hit` (or "—" if none in top-10), `any anti-expected in top-5?` (yes/no/—).

Per-query data is included on purpose: with ~26 queries, the diagnostic value of "*which* queries got better when I swapped to mxbai" outweighs the verbosity cost.

## 7. Failure modes

| Condition | Behaviour |
|---|---|
| `--cache` does not exist for `eval run` | Print clear error pointing to `eval build`. |
| Cache exists but model stamp does not match `--model` | Refuse with a clear error showing both stamps. |
| Query file malformed (bad JSON line) | Fail fast at startup with the offending line number; do not partially run. |
| Embedder model not in fastembed enum | Compile error (the model IDs are an enum, not strings, in the eval binary). |
| Build interrupted partway | Partial cache file is left on disk; user deletes it and re-runs `eval build`. No automatic cleanup. |
| Indexing failure on a specific note | Already handled by existing indexing layer — note is skipped, error is logged, build continues. The eval inherits this behaviour. |

## 8. Out of scope for Phase 1.5

- HTTP / MCP exposure of `semantic_search` (Phase 2).
- Hybrid retrieval combining FTS5 + semantic (Phase 2).
- Chunking-strategy experiments (separate eval, separate decision; chunker is held constant here).
- Auto-reindex on mismatch (the three-cache pre-build pattern replaces it).
- Statistical-significance reporting on metric deltas (~26 queries is too few; we read deltas qualitatively).
- Web UI for the harness (terminal + markdown is the audit trail).
- Resumable builds.

## 9. Required cleanup (in scope for Phase 1.5)

These follow naturally from introducing two new embedders and discovering the existing naming is wrong:

- **`src/embed/arctic.rs`** — the struct named `ArcticEmbedder` loads `EmbeddingModel::BGESmallENV15`. Rename to `BgeSmallEmbedder` (or restructure into a model-id-parameterized `FastembedEmbedder`). Two new embedders (`NomicEmbedder`, `MxbaiLargeEmbedder`) join either as siblings or as variants of a parameterized type — the implementation plan decides which.
- **Phase 1 spec §10** — candidate-models section currently lists Arctic-S / Arctic-M / mxbai-large. Update to the fastembed-compatible trio: BGE-small / Nomic-v1.5 / mxbai-large, with a footnote explaining why the Arctic variants were dropped.
- **Phase 1.5 brief** (`2026-05-18-phase-1.5-eval-brief.md`) — replace the Arctic trio with the fastembed-compatible trio. Same correction.
- **Project memory** — any entries that reference Arctic-S as the current model are stale and should be updated or removed.

## 10. Acceptance criteria

The harness is complete when:

1. `eval build` produces a valid, queryable cache for each of the three models, with progress logged and final wall-clock time reported.
2. `eval run` against any of the three pre-built caches reports the six metrics from §4 in under ten seconds for the ~26-query set.
3. `eval/results.md` contains at least one section per model from a real run.
4. The `arctic.rs` naming is fixed; the spec, brief, and memory references to Arctic-S as the current model are corrected.
5. The original `SqliteCache::semantic_search` test suite still passes.
