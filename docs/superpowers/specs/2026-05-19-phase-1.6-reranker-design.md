# Phase 1.6 — Cross-Encoder Reranker Design

> Status: design draft. Implementation plan to be drafted next via `writing-plans` once this is approved.

## 1. Goal

Add a second-stage cross-encoder reranker to the retrieval path so that the top-K embedding candidates are re-scored on the actual `(query, chunk)` text pairs before being returned. The motivation is the FP-rate@5 regression observed in Phase 1.5 after enabling Nomic task prefixes: `eval/results.md` shows FP@5 doubling from 0.250 to 0.500 (U5 leaks `idea-baby-tummy-time-…-airplane-hold` against the query "I am travelling by plane with the baby"). A reranker is the canonical fix for near-duplicate antis whose embeddings are pulled close by surface vocabulary overlap.

Like Phase 1.5, this phase ships an **evaluation-only** harness. Production wiring of the reranker into `SqliteCache::semantic_search` and the MCP surface is deferred — the eval decides whether the quality lift is worth the latency.

## 2. Comparison set

Two rerankers, both reachable from fastembed 4.9.1's `RerankerModel` enum, both chosen for CPU viability on the deployment target (VM with 4 vCPUs on an i5-11th-gen laptop):

| Model | Params | Context | Languages | Role |
|---|---|---|---|---|
| `JINARerankerV1TurboEn` | 37.8M (6-layer distill) | 8192 tok | English only | Speed floor — ~5× faster than Jina v1 base |
| `JINARerankerV2BaseMultilingual` | 278M | 1024 tok | 26 languages incl. French, Spanish | Quality target — current canonical CPU multilingual reranker |

Models considered and **dropped**:

- `BGERerankerV2M3` (568M, multilingual) — strictly heavier than Jina v2 multilingual; ~2× the inference cost on CPU for marginal quality gain in published benchmarks. Worth revisiting if both Jina rerankers underperform on the eval, but not in this phase.
- `BGERerankerBase` — English+Chinese only, older architecture, dominated by Jina v1 turbo on speed and by Jina v2 on quality.

## 3. Architecture

### 3.1 Pipeline shape

```
query
  └─> Embedder.embed(query_prefix + query)
        └─> SqliteCache.semantic_search(query_vec, k = K_initial)   // existing
              └─> Vec<SemanticHit>                                    // K_initial = 20
                    └─> Reranker.rerank(query, [hit.content; …])      // NEW
                          └─> Vec<RerankedHit>                        // sorted by reranker score
                                └─> truncate to top-N (5 or 10)
```

The reranker reads `query` (raw, no Nomic prefix — rerankers have their own pair-encoding format and are not Nomic-task-prefixed) and each candidate's `content` (the same `chunk.content` already stored in SQLite — no re-chunking, no re-embedding).

### 3.2 `Reranker` trait

New file `src/rerank/reranker.rs`:

```rust
pub struct RerankedHit {
    pub chunk_id: i64,
    pub note_slug: String,
    pub heading_path: Option<String>,
    pub content: String,
    pub embedding_distance: f32,   // preserved from retrieval for diagnostics
    pub rerank_score: f32,         // reranker output; higher is better
}

pub trait Reranker: Send + Sync {
    /// Returns the candidates sorted by descending rerank score.
    /// Length of the output equals length of the input; truncation is the caller's job.
    fn rerank(
        &self,
        query: &str,
        candidates: Vec<SemanticHit>,
    ) -> Result<Vec<RerankedHit>, String>;

    fn id(&self) -> &'static str;
}
```

A `FastembedReranker` impl mirrors `FastembedEmbedder`: constructed once at startup, loads the ONNX model from the fastembed cache, holds the `TextRerank` handle, exposes `jina_v1_turbo()` and `jina_v2_multilingual()` constructors.

### 3.3 No cache rebuild

Rerankers operate on text pairs. They do not produce or consume embedding vectors. The existing Nomic SQLite cache (`data/cache/hatchdoor-cache-nomic-v1-5.sqlite3`, built with prefix + overlap=50) is reused as-is. The eval simply reads `SemanticHit.content` and passes it to the reranker.

### 3.4 Chunking held constant

`ChunkOptions { max_tokens: 800, overlap_tokens: 50 }` stays. The decision to bump overlap was deferred precisely so the reranker is the only changed variable in this phase. If FP@5 with reranking still has slack, an overlap experiment becomes a clean follow-up phase. Do not bundle.

## 4. Eval extension

### 4.1 New subcommand: `eval rerank`

Sibling to `eval build` / `eval run`. Reuses an existing cache built in Phase 1.5; does not build anything.

```
cargo run --release --bin eval -- rerank \
  --model NomicEmbedTextV15 \
  --cache data/cache/hatchdoor-cache-nomic-v1-5.sqlite3 \
  --reranker JINARerankerV2BaseMultilingual \
  --queries eval/queries.jsonl \
  [--initial-k 20]
```

- `--reranker` accepts `JINARerankerV1TurboEn` or `JINARerankerV2BaseMultilingual`. Compile-time enum, same pattern as `--model`.
- `--initial-k` defaults to **20**. The reranker re-scores the top-20 from `semantic_search`, then the eval scores metrics at k=5 and k=10 against the reranked order.
- The embedder is still loaded, because the query still has to be embedded for the initial retrieval. The Nomic task prefix (`search_query: `) continues to apply on the retrieval side.

### 4.2 Metrics

Same six metrics as Phase 1.5 (§4 of `2026-05-18-phase-1.5-eval-design.md`): `Recall@5 (any/all)`, `Recall@10 (any/all)`, `MRR`, `FP-rate@5`. Computed against the **post-rerank** ranking.

Additional per-query columns in the markdown report (see §5):

- `Rank pre-rerank` — rank of first expected note in the 20-candidate embedding output.
- `Rank post-rerank` — rank of first expected note after reranking.
- `Δ` — `pre - post` (positive = reranker moved the answer up).

These make it cheap to see which queries the reranker helped, hurt, or left alone.

### 4.3 Latency reporting

The eval measures and reports:

- **Per-query rerank latency** — median, p90, max across all queries (the reranker is the new bottleneck).
- **End-to-end query latency** — embed + retrieve + rerank, same statistics.

Reported in the terminal summary and the markdown section header. This is the deciding signal for whether to wire the reranker into production (a 1s p90 is unusable for interactive search; a 200ms p90 is fine).

## 6. Failure modes

| Condition | Behaviour |
|---|---|
| `--cache` does not exist | Same error as `eval run`: point at `eval build`. |
| Cache model stamp does not match `--model` | Same as `eval run`: refuse. |
| Reranker model fails to download | Fail fast with the fastembed error message; do not partially run. |
| Reranker returns wrong number of scores | Fail with index assertion; this is a library bug, not a query bug. |
| Query has fewer than `--initial-k` candidates in the cache | Rerank whatever was returned; metrics still computed. |
| Reranker latency exceeds a soft threshold | Logged as a warning, not a failure. Decision to ship to production is a human read of the latency table. |

## 7. Out of scope for Phase 1.6

- **Production wiring.** `SqliteCache::semantic_search` is not modified; the MCP `vault.search_semantic` tool is not touched. Decision deferred until the eval shows acceptable quality and latency.
- **Score blending.** The reranker score replaces the embedding distance for ranking purposes within the eval; no calibration, no weighted combination. If a blend is needed in production, that's a phase-2 decision informed by what the eval reveals.
- **Chunk overlap tuning.** Held constant at 50 to keep this phase one-variable.
- **Async / batched reranking pool.** The fastembed `TextRerank::rerank` call is invoked synchronously for the 20-candidate batch. Optimizations (CPU thread pinning, ONNX session options, int8 quantization) are not in scope; the eval measures the out-of-the-box behaviour.
- **BGE rerankers.** Listed in §2 as dropped. Re-add to a follow-up phase if Jina v2 multilingual underperforms.
- **Multi-stage rerankers / listwise rerankers** (Jina v3, Nemotron). Pairwise cross-encoders are the established CPU baseline; listwise is a future-phase decision.
- **Reranker fine-tuning on the vault.** Way out of scope.

## 8. Acceptance criteria

The phase is complete when:

1. `cargo run --release --bin eval -- rerank …` runs end-to-end against the existing Nomic cache for both `JINARerankerV1TurboEn` and `JINARerankerV2BaseMultilingual`, producing two new sections in `eval/results.md`.
2. Each section reports the six metrics from Phase 1.5 §4 plus per-query pre/post rerank ranks.
3. Each section reports median, p90, and max rerank latency and end-to-end latency.
4. The existing `eval build` and `eval run` paths still work unchanged. The reranker is purely additive at the harness level.
5. The new `Reranker` trait has a passing unit test using a stub reranker (deterministic, mirrors `StubEmbedder` pattern) so future work on production wiring has a non-fastembed test scaffold.
6. The original `SqliteCache::semantic_search` test suite still passes.

## 9. Open questions for implementation/brainstorming

These are intentionally left for the implementation plan or a follow-up brainstorming pass, not decided here:

- Whether `eval rerank` should also accept a `--top-n` flag to truncate output (currently the eval scores metrics at k=5 and k=10 regardless, so probably not needed).
- Whether the reranker should be a separate Rust module crate or a sibling of `src/embed/` — leaning toward `src/rerank/` for symmetry, but the implementation plan can decide.
- How to surface the reranker in the eventual production path: drop-in replacement for the existing top-K sort, opt-in via flag/env, or a separate MCP tool. Deferred to post-eval.
