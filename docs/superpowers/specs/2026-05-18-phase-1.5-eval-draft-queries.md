## Label format (proposal, not locked)

For each query:

- `expected_notes`: one or more note slugs (filename without `.md`) that should appear in the top-k hits.
- `expected_heading_path` *(optional)*: heading path within the note where the answer sits. Useful for chunk-level grading later; safe to leave blank.
- `anti_expected` *(optional)*: notes that share surface vocabulary with the query but are semantically wrong (e.g. "gift perfume for Nadine" when the query is about house fragrance). Only used on queries where this failure mode is plausible — not every query needs them. Lets us measure false-positive rate on near-duplicate distractors.

A query can have multiple expected notes (e.g. "rebuy-worthy coffees" legitimately spans several).

## Notes / open questions surfaced while drafting

- **Phrasing register.** Drafts are in "how would a user ask" style (full sentences). If your real queries are more keyword-style ("kopia telegram failure alert"), the eval should reflect that.
- **Multi-answer queries.** #8 (rebuy-worthy coffees) needs `expected_notes` to support a list. The label format must allow that natively.
- **Heading-path label fidelity.** I'm assigning headings by eyeballing the note structure, not by inspecting actual chunk boundaries. Once we run the harness for the first time, we'll learn whether "the right heading" cleanly maps to "the right chunk". Probably fine for recall@k; less fine for chunk-level grading.
