# Phase 1.5 — Evaluation Harness Brainstorming Brief

> Hand this to a fresh Claude Code session along with `/superpowers:brainstorming` to design Phase 1.5. After reading this brief, the session should also read `docs/superpowers/specs/2026-05-18-semantic-foundation-design.md` (esp. §11.3 and §10) before asking questions.

## Where we are

Phase 1 (semantic foundation — layers 4/5/6) is **implemented and merged**. Concretely:

- Vault is chunked with `text-splitter` using the BGE-small tokenizer.
- Chunks are embedded in-process by `fastembed-rs` with BGE-small-en-v1.5 (`BGESmallENV15`, 384-dim).
- Embeddings live in the existing `hatchdoor-cache.sqlite3` via `sqlite-vec`'s `vec0` virtual table.
- `SqliteCache::semantic_search(embedder, query, k) -> Vec<SemanticHit>` is callable from internal Rust code. **No HTTP route, no MCP tool yet.**
- The `Embedder` trait is in place; swapping models is a one-line concrete-type change plus a one-time reindex (procedure in spec §11.3 and §10).

Vault scale: 286 notes, ~1,500 chunks, ~3.5 MB of vector data, ~60 s cold reindex.

## What Phase 1.5 is for

Build a small, repo-local **eval harness** that:

1. Holds a labelled query set the user wrote against their real vault.
2. Runs each query through `SqliteCache::semantic_search` with a configurable `Embedder`.
3. Scores results with a small set of retrieval metrics (likely recall@k and MRR).
4. Lets us compare BGE-small vs Nomic-v1.5 vs mxbai-large (the candidate set in spec §10) by swapping the concrete `Embedder`, doing a one-time reindex, and re-running.

This is what gates any future embedding-model swap — the user explicitly said the eval harness drives that decision.

## What the user has already decided

- **Eval set exists or will be authored** — the user committed to creating a labelled query set (answered "B" when asked).
- **Single-binary deployment stays intact** — eval can live as a `cargo test --ignored` binary or a separate `cargo run --bin eval`, but it must not require a second container.
- **No production API surface in Phase 1.5** — the harness is a developer tool, not exposed to agents.
- **Three candidate models for comparison:** `BGESmallENV15` (current, 384-dim), `NomicEmbedTextV15` (768-dim), `MxbaiEmbedLargeV1` (1024-dim). All available in fastembed-rs 4.9.1. See spec §10 for the rationale and note on why Arctic-S/M are not used.

## What still needs to be brainstormed

These are the open design questions for the next session:

1. **Query-set shape.** Plain TSV/CSV? JSONL? YAML? Format dictates how easy it is to author and version-control by hand. The user has not picked.
2. **Label format.** Per-query: list of "must-return" chunk IDs? Note slugs? Heading paths? Free-text answers and judge by overlap? Hand-labelling 50 queries is very different from hand-labelling 500.
3. **Metrics.** Recall@5 / recall@10 / MRR are the obvious starting set. Worth NDCG? Probably not at this scale.
4. **Harness entry point.** Three options:
   - Ignored `#[test]` in `tests/eval.rs` invoked as `cargo test --features eval -- --ignored`.
   - Separate `cargo run --bin eval` binary that reads a path to the query set.
   - A small CLI subcommand on the existing `hatchdoor` binary (`hatchdoor --eval <path>`).
5. **Reindex automation.** Swapping models requires `rm hatchdoor-cache.sqlite3 && cargo run --release`. Should the harness shell that out, or just print instructions and refuse to run if the index isn't built for the model under test?
6. **Output format.** Plain text table for the terminal? Markdown report committed alongside the query set? Both?
7. **Where the query set lives.** `tests/eval/queries.jsonl`? A separate `eval/` directory at the repo root? The Phase 1.5 spec needs to commit to a path.

## What NOT to brainstorm

These are decided; do not re-open in Phase 1.5:

- Embedding model catalog (spec §10).
- Where embeddings are stored (sqlite-vec in the existing cache).
- The `Embedder` trait shape — it is the abstraction Phase 1.5 swaps over.
- Whether semantic search has a public HTTP route — no, that is Phase 2.
