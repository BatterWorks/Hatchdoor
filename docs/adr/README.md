# Architecture Decision Records

This directory records the significant architecture decisions behind Hatchdoor —
what was decided, why, and what it commits us to. Read it before proposing a
structural change: each record is a **constraint your PR is expected to respect**.
If your change would break one, that's fine — but say so, and propose an amendment
(see below) rather than quietly working around it.

Most decisions are captured as short sections in this file. One decision with a
full evaluation behind it lives in its own file and is linked from the index.

## How to change a decision

These records are **append-only**. Don't rewrite an accepted decision to reflect
a new one — instead:

1. Add a new record (next number) describing the new decision.
2. Set the old record's status to `Superseded by ADR-NNNN` and leave its text intact.

This keeps the *history* of why the code is shaped the way it is, which is the
whole point.

## Template

Copy this for a new record:

```markdown
## ADR-NNNN — Short title

- **Status:** Proposed | Accepted | Superseded by ADR-XXXX
- **Context:** The problem and the forces at play (constraints, requirements).
- **Decision:** What we decided to do.
- **Consequences:** What this makes easier or harder; the tradeoff accepted.
- **Evidence:** Where this shows up in the code/docs.
```

## ADR-01 — Markdown is the source of truth; SQLite is a disposable read model

- **Status:** Accepted
- **Context:** Users own an Obsidian-style vault of `.md` files and must never be locked into Hatchdoor's storage.
- **Decision:** The `.md` files under `VAULT_PATH` are authoritative. SQLite is a generated cache built from them and safe to delete; it is rebuilt from the vault on demand. The schema is versioned and the embedder identity is stamped — a mismatch wipes and rebuilds rather than serving stale or mixed-model data.
- **Consequences:** The cache can live outside the vault and be discarded freely; schema or embedding-model changes cost a full reindex, accepted as the price of never corrupting the read model.
- **Evidence:** README "Data and Safety Model"; `cache/vault_snapshots.rs` (`replace_vault_snapshot`, the per-Vault rebuild that replaced `app_state.rs`'s `build_cache` in #185); `cache/schema.rs` (`SCHEMA_VERSION`, `reset_if_embedder_changed`).

## ADR-02 — One binary serving three surfaces over one shared core

- **Status:** Accepted
- **Context:** Hatchdoor must serve a browser UI, AI agents, and static assets, on modest self-hosted hardware, with a simple deploy story.
- **Decision:** A single `axum` binary exposes three surfaces — a JSON HTTP API, an MCP server at `/mcp`, and the built React SPA as static files — over one shared domain core and one `AppState`.
- **Consequences:** One container, one process, shared state; the cost is a large composition root (`server.rs`) that concentrates routing and startup logic.
- **Evidence:** `server.rs` router construction; `app_state.rs`.

## ADR-03 — Web and MCP writes share one `vault/write/` layer

- **Status:** Accepted
- **Context:** Both the browser and agents can mutate the vault. Divergent write paths would mean divergent safety guarantees — the class of bug that loses user data.
- **Decision:** All mutations go through the atomic primitives in `vault/write/`. The HTTP write API and the MCP write tools are thin adapters over the same functions. Writes use a content-hash (`expected_content_hash`) for optimistic concurrency.
- **Consequences:** One place to audit for data-loss safety; both surfaces get path-safety, link-rewriting, and atomic rename for free. Adapters must not reach past this layer to touch the filesystem.
- **Evidence:** `vault/write/{notes,attachments,fs_ops,rewrites}.rs`; `handlers/write_api.rs`; `mcp/tools/write.rs`.

## ADR-04 — Local, CPU-only embeddings; no external inference API

- **Status:** Superseded by ADR-16
- **Context:** Hatchdoor targets private, self-hosted deployment on modest hardware. A dependency on a paid or remote inference API would break privacy and offline operation.
- **Decision:** Embeddings run locally via fastembed (Nomic Embed Text v1.5, 384-dim). Model weights are prefetched at image-build time so first run is offline.
- **Consequences:** Fully private and offline; embedding is CPU-bound, which directly constrains the search-strategy decision (ADR-05).
- **Evidence:** `embed/fastembed_embedder.rs`; `main.rs --prefetch-embedder`; Dockerfile prefetch stage.

## ADR-06 — Embedded SQLite: FTS5 + sqlite-vec, WAL, pooled reads

- **Status:** Accepted
- **Context:** The read model needs keyword search, vector search, links, and stats, with zero external infrastructure and good concurrent-read behavior during reindex.
- **Decision:** Bundle SQLite (no external database, no ORM). Use FTS5 for keyword search and `sqlite-vec` for vectors. Build in memory; run in WAL mode with a pool of read connections. Reindex commits in one transaction so readers keep serving the prior snapshot.
- **Consequences:** No infra to run; hand-written SQL instead of an ORM; reads stay parallel and non-blocking during a refresh (fixes F-03/F-05).
- **Evidence:** `Cargo.toml` (`rusqlite` bundled, `sqlite-vec`); `cache/schema.rs`; `cache/queries/`; CHANGELOG F-03, F-05.

## ADR-07 — Fail-fast security posture at startup

- **Status:** Accepted
- **Context:** A self-hosted app is easy to misconfigure into exposing a private vault (binding `0.0.0.0` without auth; enabling a public demo alongside write surfaces).
- **Decision:** Refuse to start in unsafe configurations rather than warn: no non-loopback bind without `HATCHDOOR_WEB_BEARER_TOKEN`; demo mode is incompatible with MCP or git sync and refuses to boot together.
- **Consequences:** Misconfiguration fails loudly at startup instead of silently exposing data; operators must set a token before going public.
- **Evidence:** `server.rs` (`check_web_auth_posture`, `check_demo_mode_posture`, `check_demo_mode_registry_posture`); CHANGELOG F-01.

## ADR-08 — Bearer-token auth with a query-param fallback

- **Status:** Accepted
- **Context:** When set, a bearer token must protect `/api/*`, `/vault-assets/*`, and downloads. But images, SSE streams, and download links can't carry an `Authorization` header from the browser.
- **Decision:** Accept the token via `Authorization: Bearer` or, where headers can't be set, an `access_token` query parameter. Compare tokens in constant time; redact them from logs. The PWA prompts for the token on a 401 and stores it locally.
- **Consequences:** Works with header-less browser contexts; the query-param path is a deliberate, documented tradeoff (tokens can appear in URLs/proxy logs).
- **Evidence:** `config.rs` (`web_bearer_token`); `auth.rs` (`constant_time_eq`, redaction); CHANGELOG F-01, F-06.

## ADR-09 — MCP off by default, own token, Origin allowlist

- **Status:** Accepted
- **Context:** MCP exposes the whole vault to agents and is mounted at `/mcp`, outside the web-auth layer. Browser-originated JSON-RPC also invites DNS-rebinding attacks.
- **Decision:** MCP is disabled unless explicitly enabled. Even read-only MCP requires its own bearer token. Requests are checked against an Origin allowlist (localhost variants only) to block DNS rebinding. The Streamable-HTTP protocol is implemented directly.
- **Consequences:** Enabling agent access is a conscious, credentialed step; the vault is never exposed by simply turning MCP on.
- **Evidence:** `mcp/config.rs` (`validate`, `validate_mcp_request`, Origin matching); `mcp/tools/{read,write}.rs`.

## ADR-10 — Optional git sync as a debounced background task

- **Status:** Superseded by ADR-18 for the mechanism (the instance-wide debounced task over `VAULT_PATH`); the safety decisions below (opt-in, never force-checkout over uncommitted manual edits, local mode never contacts a remote, writes do not block on sync) remain in force and are restated there for the per-Vault Git turn.
- **Context:** Users want their vault edits versioned and pushed, without blocking writes or fighting manual git usage.
- **Decision:** Optional (off by default) auto commit-and-push via vendored `git2`, on a debounced background loop with conflict-abort semantics. It refuses to force-checkout over uncommitted manual edits to tracked files, surfacing them as an error. The watcher ignores `.git/` so sync churn doesn't trigger reindexing.
- **Consequences:** Writes stay fast (sync is async); manual edits are never silently discarded; sync is opt-in.
- **Evidence:** `git/{sync,task,message}.rs`; CHANGELOG v2.1.0, F-08.

## ADR-11 — Soft delete (trash) and archive-by-move

- **Status:** Accepted
- **Context:** Agents and the UI can delete or archive notes. Destructive deletes on user data are unacceptable.
- **Decision:** Delete moves notes, and the referenced assets that live inside the note's own folder, into `.hatchdoor-trash` (excluded from indexing). A referenced asset kept elsewhere stays where it is. Archive moves notes under `HATCHDOOR_ARCHIVE_PREFIX` (default `90-archive/`), which also drives archived-link styling.
- **Consequences:** Deletes are recoverable; nothing is unlinked from disk by Hatchdoor. The trash folder is skipped when deciding whether a vault is empty.
- **Evidence:** README "Data and Safety Model"; `vault/write/`; `config.rs` (`archive_prefix`); CHANGELOG F-12. Asset travel was narrowed to the note's own folder in #225 (`vault/write/assets.rs`, `asset_move_plan`).

## ADR-12 — Distroless, rootless, multi-stage container

- **Status:** Accepted
- **Context:** The shipped image should have minimal attack surface and run without root.
- **Decision:** Runtime is `distroless/cc` as `nonroot`. The build is multi-stage (cargo-chef dependency cache → Rust build → separate frontend build → slim runtime). Because the runtime has no shell, the health probe is a `--healthcheck` subcommand built into the binary.
- **Consequences:** Small, rootless, shell-less image; anything needing a shell (like a curl-based healthcheck) had to move into the binary.
- **Evidence:** `Dockerfile`; `main.rs` (`run_healthcheck`); CHANGELOG F-17.

## ADR-13 — Deliberate minimalism: trait seams only where they pay

- **Status:** Accepted
- **Context:** It's tempting to add abstractions "for flexibility" — traits, a state-management library, an ORM, a CSS framework.
- **Decision:** Introduce abstraction only where it earns its keep. The only trait seams over external ML dependencies are `Embedder` and `Reranker`, exactly where test doubles (`StubEmbedder`) and the `embedder-tests` feature gate need them. No Cargo workspace, no ORM, no frontend state library, no CSS framework.
- **Consequences:** A lean, navigable dependency set; new code should follow suit rather than introduce speculative layers.
- **Evidence:** `embed/embedder.rs`, `rerank/reranker.rs`; `Cargo.toml` / `frontend/package.json` dependency sets.

## ADR-14 — No deployment step requires a browser

- **Status:** Accepted
- **Context:** A Hatchdoor deployment must be completable end to end by a script, a compose file, or an agent, with no human at a browser to finish the boot. That pulls against the settings page: once a knob is editable in the UI, the pull is to make the UI its home and drop the environment variable behind it.
- **Decision:** No step required to bring Hatchdoor to a working state may be reachable only through the browser. For operator settings the mechanism is an environment variable, and that variable is authoritative for the process — the durable `settings.json` overlay resolves beneath the environment pins and above the defaults, and the UI renders a pinned value as locked with its source rather than silently discarding the edit. A setting may be added to the UI, but never *only* to the UI. For anything that is not a setting, the mechanism is an API or MCP path instead. Accepting the Gemma licence is the standing example: it is a deliberate act by a person or their delegated agent, not a config default to be copy-pasted out of someone else's compose file, so it deliberately has no environment variable — but `accept_gemma_terms` / `decline_gemma_terms` over MCP let an agent complete it unattended, and the versioned on-disk receipt persists it across restarts.
- **Consequences:** A first boot from `.env` alone — plus, where a licence is involved, one agent call — is always a complete deployment, and a vault can be redeployed from scratch with no manual step. The cost is that every new setting is three things (a key in `live_settings_defaults`, a UI row, and the locked/source display), every new startup gate must ship a machine path alongside its UI, and a setting that cannot be expressed as a string in an env var does not get added.
- **Evidence:** `runtime_config.rs` (`live_settings_defaults`, `SettingSource`, `ResolvedSetting::pinned`); `handlers/settings.rs` (`SETTINGS`, `locked`, `source`); `model_setup.rs` (`accept_gemma`, `acceptance_is_current`); `mcp/tools/`; `.env.example`; README operator configuration contract.

## ADR-15 — Search quality is a product feature, not a tunable

- **Status:** Accepted
- **Context:** Retrieval quality is the reason to run Hatchdoor at all. It is also the easiest thing to erode by accident — a cheaper embedding model, a chunking tweak, a filter added for speed, a smaller candidate count. Each looks locally reasonable, and none of them announce themselves as a regression.
- **Decision:** No change may knowingly degrade retrieval quality. Any change touching the retrieval path — embedding model, chunk size or overlap, contextual document headers, task prefixes, layer selection, candidate counts, pre- or post-filters — is validated against the eval set in `eval/` before merge, on the same metrics the harness already reports (Recall@5/10, MRR, FP-rate@5, correct-heading), with the per-category and per-tier breakdown read, not just the aggregate. Where quality and another axis conflict, quality wins: prefer paying latency, memory, disk, or index time over recall or ranking. A regression ships only with an explicit recorded justification and its measured cost.
- **Consequences:** Retrieval changes cost an eval run and usually a full reindex, so they move slower than other work. Optimisations on the search path must prove neutrality rather than assume it. Swapping the embedder is a deliberate, evaluated decision (ADR-16), never a convenience.
- **Evidence:** `eval/` harness, `eval/queries.jsonl`, `eval/results.md`; `docs/research/embeddings/`; `cache/schema.rs` (embedder-identity stamp forcing a rebuild on model change).

## ADR-16 — EmbeddingGemma by default behind a licence gate; representation locked at 800/50 with context

- **Status:** Accepted (supersedes ADR-04)
- **Context:** ADR-04 fixed the principle — local, CPU-only embeddings, no external inference API — but named Nomic Embed Text v1.5 at 384 dimensions with weights baked into the image. The 2026-07 embedding sweep replaced both halves of that. It ran a 24-cell grid over models, chunk settings, and contextual documents against an eval set grown from 26 queries to ~125, tiered and categorised. Separately, shipping Gemma weights in a public image is not something the licence permits us to do on the user's behalf.
- **Decision:** The principle of ADR-04 stands unchanged: embeddings run locally on CPU via fastembed, with no remote inference. What it resolves to now is EmbeddingGemma 300M Q4 at 768 dimensions — multilingual, with its own retrieval query/document prefixes — as the default, and Nomic Embed Text v1.5 as the fallback for a user who declines the Gemma terms, explicitly labelled English-only and lower quality for multilingual vaults. Public images ship neither model; weights are fetched on first run behind the licence gate (ADR-14). The document representation is locked at 800-token chunks, 50-token overlap, and contextual headers on: context off wins raw recall, but context on wins MRR in 11 of 12 like-for-like comparisons and correct-heading accuracy in all 12, and Hatchdoor routes people into a specific note section, so first-result quality and heading accuracy are worth more than the broader recall. ADR-05 was re-validated against this newer evidence and is unchanged — retrieval stays pure semantic, with reranking and hybrid fusion offline evaluation tools only.
- **Consequences:** First run is no longer offline: it needs a network fetch and a licence decision, which is why that decision has a machine path. The cache carries the embedder identity, so switching models wipes and rebuilds. 450/50 with context on remains the specialist setting for heading navigation and is not the default. Any future move off these values is an ADR-15 change and needs eval numbers.
- **Evidence:** `embed/fastembed_embedder.rs` (`embedding_gemma_300m_q4`, `DocumentFormat::GemmaRetrievalV1`); `model_setup.rs`; `chunk/chunker.rs` (`max_tokens: 800`, `overlap_tokens: 50`); `docs/research/embeddings/embedding-sweep-decisions-2026-07-26.md`; `eval/results.md`; CHANGELOG v2.4.0.

## ADR-17 — RMCP is the MCP protocol boundary; supported revisions narrow to 2026-07-28 and 2025-11-25

- **Status:** Accepted (supersedes the single sentence of ADR-09 that reads "The Streamable-HTTP protocol is implemented directly"; every other ADR-09 decision — MCP off by default, its own bearer token even for read-only access, and the Origin allowlist against DNS rebinding — remains fully in force)
- **Context:** Hatchdoor's `/mcp` surface is a hand-written, POST-only Streamable HTTP adapter under `src/mcp/`, serving exactly three legacy revisions (`2025-03-26`, `2025-06-18`, `2025-11-25`). The MCP specification's `2026-07-28` revision adds stateless discovery-based requests, per-request protocol metadata with required HTTP headers, subscription streams, Multi Round-Trip Request (MRTR) wire types, and typed results with machine-readable output schemas. Hand-implementing all of that would grow a bespoke wire layer that every future protocol revision would have to re-earn inside our own code. The refreshed migration baseline (`docs/research/mcp-2026-07-28-refresh.md`, ticket #163) confirmed the parts we own are healthy and must not change: the explicit `vault_id`/`scope` tool catalogue (35 tools), the per-request security ordering, structured error semantics, and the shared `vault/write` mutation layer. The reconciled migration package (#43, corrected by #164) chose a deep protocol boundary: future revisions should arrive through an SDK upgrade, not through re-writing transport code.
- **Decision:** Two halves, decided together:

  1. **Adopt stable rmcp 3.x as the MCP protocol boundary**, pinned to exactly `rmcp = "=3.1.4"` in Cargo.toml (an exact-version requirement; published on crates.io 2026-08-20; MSRV 1.88; Apache-2.0). RMCP owns JSON-RPC framing, Streamable HTTP serving, lifecycle and version negotiation, discovery, request `_meta`/header validation, subscription streams, MRTR-aware wire types, and version-specific serialization. The existing tool catalogue and dispatcher remain framework-independent behind a typed adapter implementing rmcp's `ServerHandler` seam; the 35 tools are NOT rewritten into rmcp's macro-generated route tables.
  2. **Narrow the advertised protocol revisions to exactly `2026-07-28` and `2025-11-25`.** Modern clients work without any initialization handshake — `server/discover` replaces `initialize` for them, and requests are served statelessly. Legacy clients keep the existing initialize/negotiation flow unchanged. `2025-03-26` and `2025-06-18` are no longer advertised (`2024-11-05` was already absent).

  The trait/type surface above was verified against the actual crate source before acceptance — tag `rmcp-v3.1.4`, commit `4a738b9dd99eaca418b614afa433a0cbdaf8d056`:

  - MRTR types (SEP-2322 `InputRequiredResult`, version-gated to ≥ `2026-07-28`): `crates/rmcp/src/model/mrtr.rs`.

  **Branching revision:** implementation happens on a single feature branch `feature/mcp-2026-07-28`, cut from current `development` and merged back via PR after verification (ticket #172). This supersedes item 11 of the #43 decision package: the previously planned stacking on `feature/ui-ux-polish` is obsolete because that content has already landed on `development`.
- **Consequences:** Future MCP protocol revisions primarily arrive through rmcp upgrades instead of hand-written wire code; each upgrade becomes a deliberate, reviewed event against this record's pin. The hand-written JSON-RPC/transport code in `src/mcp/protocol.rs` and `src/mcp/routes.rs` shrinks into a thin adapter, so the boundary keeps its file inventory only if the map is updated when files move (module-map rule). Security posture must be re-expressed at the new boundary without weakening: the per-request ordering enabled check → token configured → Origin allowlist → constant-time bearer compare → protocol-version header, plus the v2.5.0 rule that the MCP token works on the attachment endpoint only while MCP *and* MCP write mode are live-enabled; a dedicated regression test proves it survives the swap (#172). Rate limiting (#171), subscriptions/listen with honest `listChanged` (#170), the modern surface (#169), and typed results/outputSchema for all 35 tools (#167) build directly on this seam. Golden wire tests lock both supported revisions across the replacement. Costs accepted: one additional dependency tree (rmcp + tower/hyper ecosystem pieces already present via axum), an MSRV floor of Rust 1.88, and the discipline of keeping domain logic out of the adapter.

## ADR-18 — Per-Vault Git turns supersede the single-Vault debounced sync task

- **Status:** Accepted, except for the sentence "The commit-on-write debounce has no successor", which is superseded by ADR-23, and the clause "scheduled through the coordinator with no second execution lane", which is superseded by ADR-31 (supersedes ADR-10's mechanism only; every ADR-10 safety decision remains in force and is restated below, and every one of them still binds the commit turn ADR-23 adds)
- **Context:** ADR-10 fixed optional Git sync as one debounced background task over the process-wide `VAULT_PATH`, started from the settings page and locking phase by phase against an instance-wide write lock. The Vault collection runtime (v2.5.0) changed the unit of work: each Vault carries its own definition (source kind, Git mode, credentials, poll interval, commit identity) and gets its own Git turn, requested through the shared `VaultWorkCoordinator` by the managed-Git scheduler, a manual sync or retry, or activation, and executed by runtime composition under that Vault's mutation lock. The old task still compiled and was still reachable from the settings Git lifecycle, which gates on a value the collection runtime never sets, so in production it answered 503; the architecture review of 2026-08-28 (#162) found the two mechanisms had diverged on locking granularity, drift handling, and recovery, and that the instance-wide Versioning console and `/api/git-status` reported only the dead task.
- **Decision:** The per-Vault Git turn is the only Git synchronisation mechanism. One turn per Vault, one operation at a time, scheduled through the coordinator with no second execution lane; a turn holds that Vault's mutation lock for its whole blocking duration; the Vault's source kind and Git mode select the operation (acquire-or-reuse then synchronise a managed checkout; synchronise an existing checkout with its one configured remote; commit local history without touching a remote). ADR-10's safety decisions are restated for the turn: sync is optional and off per Vault by default; a turn never force-checks out over uncommitted manual edits, reporting a dirty working copy or a conflict as a structured, non-retryable error with the affected paths; local-history mode never contacts a remote; writes never block on sync except for the one Vault whose turn is running. The instance-wide debounced task, its handle, its write-record hook, and the instance-wide write lock are removed (#185). The boot-time parse of `HATCHDOOR_GIT_*` is deliberately kept, now serving only two purposes: refusing to start on a half-configured Git mode, and feeding the demo-mode posture refusal. No runtime behaviour reads its result. `HATCHDOOR_GIT_AUTHOR_NAME` and `HATCHDOOR_GIT_AUTHOR_EMAIL` remain as the commit-identity fallback for a Vault without its own and are read per turn (#181); the other `HATCHDOOR_GIT_*` keys remain only as first-boot import inputs until #82 closes.
- **Consequences:** One Git code path to audit, and Git behaviour that is configured, reported, and controlled per Vault (status, error detail, `Sync now`, `Try again`). The per-turn lock is coarser than the old per-phase lock: a foreground write to a Vault waits while that Vault's turn runs, a trade accepted in #96 over a finer discipline. The commit-on-write debounce has no successor: the watcher's fixed debounce coalesces writes into the next turn, and the per-Vault poll interval answers how often to look at the remote. The settings page loses its instance-wide Versioning console and `/api/git-status` is retired (#183).
- **Evidence:** `git/managed_task.rs` (`run_managed_git_turn`, `run_existing_git_remote_turn`, `ManagedGitScheduler`), `git/managed_sync.rs` (`synchronize_managed_checkout`), `git/managed_checkout.rs` (`acquire_or_reuse`), `git/sync.rs` (`run_local_history_git_turn`), `vault_executor.rs` (`dispatch_git_turn_with`, `plan_git_turn`, `publish_managed_git_turn_outcome`; extracted from `vault_runtime.rs` in #197), `vault_registry.rs` (`VaultGitMode`, `poll_interval_secs`, `commit_identity`); #162, #181, #183; issues #94–#97, #132 for the per-Vault turn's history. The removal itself landed in #185: `git/task.rs` and `git/status.rs` are deleted outright, `git/sync.rs` keeps only the local commit path (`validate_repo`, `validate_local_repo`, `init_local_repo`, `commit_local`, `run_local_history_git_turn`) with its fetch/integrate/push, unpushed accounting, and merge-marker recovery gone, `AppState` loses `git_sync`, `vault_write_lock`, and `startup_git_config`, `server.rs` loses the sync-task shutdown drain but keeps the boot-time `HATCHDOOR_GIT_*` parse for configuration validation and the demo posture check (`server.rs`, `legacy_git_config` into `check_demo_mode_posture`), and `handlers/settings.rs` loses `patch_settings_with_git_lifecycle` and `production_sync_ops`.

## ADR-19 — Vault-qualified cores are the only seam an adapter crosses

- **Status:** Accepted (refines ADR-02 and ADR-03; supersedes neither)
- **Context:** ADR-02 promises one shared core behind three surfaces and ADR-03 one write module behind thin adapters. The adapters did not stay thin. The HTTP and MCP write adapters each re-implemented the same orchestration around `vault/write` (Vault gate, capability check, per-Vault lock, authoritative index build, entry lookup, noise and marker refusal, archive-prefix resolution, off-thread execution, error typing) at 1,224 and 1,499 lines, and had drifted: MCP ran writes on the async runtime while HTTP offloaded them. Sixteen MCP tools reached the domain by calling axum handler functions with hand-built extractors and decoding the HTTP response body through a byte cap and two serialisation passes, so a tool could only be tested with the transport on both sides. Vault collection management (registry commit, runtime reconcile, revision response, projections, the structured error type) lived in an HTTP handler that MCP imported as a library. `VaultReadCore` and `VaultSearchCore` already showed the intended shape: a Vault-qualified core with a small interface, consumed by both adapters (#162).
- **Decision:** Four Vault-qualified cores are the seams adapters cross: `VaultReadCore` (exact reads, collection reads, contained resources), `VaultSearchCore`, the Vault mutation core (every write primitive with its orchestration; #184, #186), and the Vault collection management module (#187). HTTP handlers and MCP tools are wire-shaping adapters: they parse the transport's input, call exactly one core, and map the core's typed outcome or its structured error `{code, message, vault_id?, retryable}` to a status code or a tool error. An adapter never calls another adapter (no MCP-to-handler proxying; #188), never reaches past a core to `vault/write`, the registry, the runtime, the scheduler, or the filesystem, and holds no policy a core could hold. Cores own the off-thread execution of blocking work. The cores stay plain structs (ADR-13): no trait seam is added to formalise them.
- **Consequences:** Domain behaviour is tested once, at a core's interface, with a filesystem fixture; each adapter keeps one mapping test per route or tool. A new surface or tool costs a mapping, not a re-implementation, and a new write primitive reaches every surface at once. Wire shapes do not change when orchestration moves; relocating a wire type follows the interface-change checklist. The module map gains two boundaries and its adapter sections shrink to wire shaping. Until #184–#188 land, the HTTP handlers remain the de facto library MCP calls, and that is the debt this record retires.
- **Evidence:** `vault_read.rs` (`VaultReadCore`), `search/vault_scoped.rs` (`VaultSearchCore`); #162 and its child tickets #184, #186, #187, #188; `docs/architecture/module-map.md` (Vault-qualified read projections, HTTP adapters, MCP adapter).

## ADR-20 — Deleting provably dead retrieval code needs a proof, not an eval run

- **Status:** Accepted (refines ADR-15; supersedes neither. ADR-05 needs no exemption — see Context)
- **Context:** ADR-15 requires any change touching the retrieval path, "pre- or post-filters" named explicitly, to be validated against the eval set before merge. #210 removed `NoteFilters`, `include_properties`, the property projection they drove, the branch selecting between two semantic retrieval implementations, and `semantic_hits` behind it — code that sits squarely on that path and could not run. Every producer of a `VaultSearchRequest` built the filters empty (the web search route, the `search_notes` adapter, the eval harness), `search_notes` refuses a `filters` argument at the protocol level with a test pinning the refusal, and the branch was guarded by `!request.filters.is_empty()`. The three live call sites of `NoteFilters::matches` were a no-op by construction: each check is an `all()` over an empty iterator and the property arm returned `is_empty() && is_empty()`, so it answered `true` for every note. Read literally, ADR-15 demanded an eval run for a deletion that no eval could speak to: the harness measures what executes, and the claim was that this did not. Running it would have reported the same numbers for a reason unrelated to the change, which is a weaker statement than the proof already in hand, not a stronger one. ADR-05 was cited alongside ADR-15 in that PR but was never actually in tension: its constraint is against *adding* reranking or FTS/vector fusion to the runtime path, and a deletion adds nothing.
- **Decision:** An eval run is not required to delete retrieval-path code when all four hold, and every one of them is recorded in the PR:

  1. **The code is dead, and the proof is by enumeration.** Either (a) it is unreachable — a guard no producer in the crate can satisfy — or (b) it executes but is provably an identity for every input any surface can construct. Both are established by listing every producer of the input and reading the callee's own definition. "I could not find a caller" is not this proof; neither is "this is always a no-op in practice."
  2. **It is a deletion.** Code that survives the change is not modified on the strength of this record. A deletion bundled with a behavioural tweak forfeits the exemption for the whole change.
  3. **A before/after comparison is measured, not argued.** The pre-change and post-change builds are run over the real surfaces against fixtures, covering each retrieval route the deletion touches, and return identical results, order, scores and payload bytes. Any field that legitimately differs is named and explained.
  4. **Doubt resolves to the eval.** If the enumeration is incomplete, the identity argument leans on typical rather than all inputs, or the comparison differs anywhere unexplained, ADR-15 applies unchanged.

  Wire shapes that were only ever produced by the deleted code are pinned by a test asserting the *serialized* output, so a later change cannot quietly turn a constant into something else.
- **Consequences:** Dead weight on the retrieval path can be removed at the cost of an argument rather than a reindex and an eval run, which is what makes removing it likely to happen at all — ADR-15's literal reading gave a standing incentive to leave unreachable code where it sat. The exemption is deliberately hard to claim: it demands an enumeration a reviewer can check line by line, and it collapses to ADR-15 the moment the deleted code turns out to have run. It says nothing about adding, tuning, or reordering anything on the retrieval path, where ADR-15 stands in full. The risk accepted is a wrong reachability proof, and it is mitigated by condition 3: a deletion that changes behaviour shows up as a differing result before it reaches `development`.
- **Evidence:** #210 and its PR #211 (the enumeration of producers, the `debug_assert!(!request.filters.is_empty())` that stated the dead branch's own precondition, and the eight-case keyword/semantic/tag comparison over the MCP endpoint and the HTTP search route returning identical results, order, scores and bytes); `search/mod.rs` and `search/vault_scoped.rs` as they stand after the deletion; the surviving `search_rejects_legacy_metadata_filters` test; `eval/` harness and ADR-15 for everything this record does not exempt.

## ADR-21 — A saved query is derived state, over a refused-by-default subset of Bases

- **Status:** Accepted
- **Context:** #19 asked for structured metadata querying and v2.3.0 delivered it; the multi-vault rewrite retired the tool that carried it and put nothing back, so selecting notes by tag, path or frontmatter property is currently impossible. #272 then asked for the next thing up: a query definition that lives *in* a note, evaluated on read and displayed as a table, so that "active subscription" means one thing to a person and to every agent instead of being reconstructed differently on each request. The reporter asked specifically for compatibility with Obsidian Bases, the built-in feature that already does this in the editor many Hatchdoor users keep pointed at the same vault directory. Two forces pull against granting that as stated. Obsidian publishes no specification, no version field and no deprecation policy for the format, is closed source, and already shipped one breaking syntax overhaul in 1.9.2, so "compatible with Bases" is a promise nothing can be checked against. And a note whose displayed content is not in the file collides with ADR-01, which is the record everything else in Hatchdoor rests on.
- **Decision:** Four parts, decided together during the triage of #272.

  1. **A query result is derived state and never vault content.** It is recomputed on every read, never written into the Markdown, and absent from search, backlinks, statistics and the graph. Indexing it would mean the read model holding content no file contains, and keeping that correct would require tracking which saved query depends on which notes and re-embedding a dependent note on every edit of a matching one. ADR-01 stays literally true: the file is the whole truth about the note.
  2. **A saved query is evaluated on demand, against the vault its note lives in, within an enforced ceiling.** On demand rather than precomputed, because a filter comparing against the current time changes its answer with no file change, so a stored result is wrong on a schedule. Its own vault only, not widenable by the definition or by the caller, because a definition whose answer depends on who asks is not a definition. The ceiling on notes scanned and rows returned is Hatchdoor's, separate from the row limit the author sets, and hitting it is reported rather than silently truncating.
  3. **Hatchdoor implements a documented subset of the Bases syntax and refuses the rest.** The subset covers filters over tags, note properties and path, comparison and boolean operators, emptiness checks, the current time, column selection and a row limit. Anything outside it is refused with the offending construct named. Refusal splits by effect: a construct that changes *which rows appear* refuses the whole saved query, since there is no honest partial answer to a filter only partly understood, while a construct affecting *only presentation* renders correct rows with the ignored instruction stated. The three outcomes, refused, empty and populated, are distinguishable on every surface, and broken never presents as empty. No Hatchdoor-only key is added to the format, which is why row sorting is viewer state rather than something the definition carries. Where a note holds more than one saved query and one of them has to be addressed by name, that identifier is Markdown *outside* the block, an HTML comment of the form `<!-- hatchdoor-query: name -->` immediately preceding it. That placement is the decision, not an incidental detail: anything inside the block, including a name on the fence line, changes what Obsidian is asked to parse, and there is no specification against which to check that it still parses. A marker outside the block cannot affect how Obsidian reads it.
  4. **Note reads never render.** An exact note read returns the authoritative Markdown always, with no argument that changes it, and reports only that a saved query is present. A separate read evaluates it and returns structured rows. Writes are guarded by a content hash of the real file, so a response pairing computed content with a valid hash would let an agent commit derived rows into the note on its next edit and turn a live saved query into a stale snapshot. Keeping rendering out of the note read makes that impossible by construction rather than merely discouraged.
- **Consequences:** Vault authors get one definition that means one thing to every reader, which is the whole point of the feature, and portability with Obsidian holds for simple definitions and visibly fails for complicated ones instead of silently disagreeing. Searching for a value that appears only in a computed row will not find the note displaying it, which is the price of part 1 and the most likely thing a future contributor will try to "fix". Agents pay one extra call to get rows and are handed data rather than a drawn table, which is the better end of that trade. The subset will look arbitrarily narrow to anyone comparing against Obsidian's documentation, and widening it is ordinary work; accepting syntax that has not been implemented is not. Standalone `.base` files stay unread, so a user who keeps definitions outside notes sees nothing until that is designed, which is a deliberate deferral rather than a rejection. Nothing here touches the retrieval path, so ADR-15 is not engaged: a query selects and does not rank, and it must stay that way for that to remain true.
- **Evidence:** #272 and its triage; the subset, refusal and ceiling contracts in #275, #276 and #277; the query capability this builds on in #274; `CONTEXT.md` (**Query**, **Saved query**, **Query result**, **Note property**); ADR-01 for why derived rows stay out of the read model, ADR-03 for the write path whose content hash makes part 4 necessary, and ADR-19 for the core both surfaces reach evaluation through.

## ADR-22 — A partial write leaves the text it did not name byte for byte

- **Status:** Accepted (refines ADR-03; supersedes nothing)
- **Context:** `update_frontmatter` was written as a merge: parse the block into a map, apply the caller's keys, serialize the map back. That is the obvious shape and it is quietly destructive. `serde_json::Map` is sorted, so the author's key order was gone before anything was written, and `serde_yaml_ng` emits every sequence in block form, so a one-line `tags: [a, b, c]` came back as five lines. Setting one field rewrote the whole block. Across the maintainer's vault, the demo vaults and both shipped sample vaults, 530 of the 531 notes carrying frontmatter use a one-line list, so effectively every call reformatted the note it touched, and the diff for a one-field change buried that change in noise deep enough to make `git blame` on frontmatter useless (#257). The behaviour was not an accident. It was documented in the function's own doc comment and pinned by two tests. What made it wrong was never the emitter's taste in YAML. It was that the tool rewrote text nobody had handed it.
- **Decision:** Text the caller did not supply is not Hatchdoor's to rewrite. A write that replaces a note's whole content may normalise what it was given, and the CRLF and trailing-newline handling on `update_note` is exactly that, and stays. A write that names a *part* of a note leaves every byte outside that part as it was: order, whitespace, quoting style, flow versus block collections, comments, blank lines. Where a named part is replaced, its replacement inherits the shape the author used for it. Where there is no prior shape, because the part is new or its kind changed, the house style is written and the caller gets no say in it. When the named part cannot be located and replaced unambiguously, and a key written twice in the same block is the case that occurs, the whole call is refused, naming the part and the reason, rather than guessing. A part the caller did *not* name is never a reason to refuse: it is copied, oddities and all, and any existing quality warning about it still fires. The one exception is the backstop, and it is deliberate: an editor doing text surgery has to prove its own work, so the edited text is reparsed and compared against the merge that was asked for, and a mismatch refuses the call. That can refuse an edit over a part nobody named, when the file is laid out in a way the editor reads differently from a YAML parser. Refusing there is the right trade, because the alternative is writing a file whose meaning has quietly changed.
- **Consequences:** A one-field change produces a one-line diff, so frontmatter maintenance across many notes becomes something an agent can do without wrecking the history, and `rename_tag` (#242) can be built on the same in-place editor rather than avoiding this layer. The cost is that the write layer now parses the block twice, once to know what it means and once to prove the edited text still means that, and carries a small text scanner for locating top-level keys. That is more code than `to_string`, and it has to stay honest about the YAML it cannot handle. The reparse check is what keeps it honest: an edit whose reparse does not match the intended merge is refused rather than written. Two refusals exist that did not before, and one class of note, a block with a duplicated key, is now editable only through its unambiguous keys. Nothing repairs a note an earlier call already reformatted; the fix is forward-looking.
- **Evidence:** `src/vault/write/frontmatter.rs` (`edit_frontmatter_block`, `top_level_keys`, `render_key`, and the reparse check before returning); `src/vault/write/notes.rs` (`update_note_frontmatter`); the tests in `src/vault/write/tests.rs` named for this behaviour, which replaced the two that pinned the alphabetised, block-style output; #257 as the worked example; #316 for the body text, where `append_note`, `edit_note` and `replace_section` in `src/vault/write/notes.rs` convert only the caller's text to the note's own line ending (`prepare_inserted_text`, `Splice::join`) instead of normalising the whole note; ADR-03 for the layer this constrains, and ADR-01 for why the file's own bytes are the thing worth protecting.

## ADR-23 — Committing is not syncing, so a commit turn is its own kind of background work

- **Status:** Accepted, except for the clause "so there is still one execution lane per Vault and no second scheduler", which is superseded by ADR-31 (supersedes one sentence of ADR-18, "The commit-on-write debounce has no successor"; every other ADR-18 decision, and every ADR-10 safety decision ADR-18 restates, remains in force and binds the commit turn added here)
- **Context:** ADR-18 made the per-Vault Git turn the only Git mechanism, and it welded two operations into it: commit the Vault's own changes, and talk to the remote. Both then ran on one schedule, and that schedule existed only because a remote needed polling. The consequences took a year to show up as one bug (#267). A Local-history Vault has no remote, so it has no poll interval, so `ManagedGitScheduler` never tracked it, so nothing requested a turn for it after the one at activation, and manual sync refused it for the same reason. Every note written to it sat uncommitted until the process restarted, while the Vault's status read `ready` and its writes returned `ok`. Two-way had the same defect in a milder form: its commit lived inside the turn that fetched and pushed, and that turn ran on the sync schedule, which defaults to once a day. The file watcher noticed every change within its debounce window and asked only for a reindex. Meanwhile the two operations have nothing in common on cost or failure. Committing is local, needs no network, and cannot fail for a reason outside the machine. Fetching and pushing cost a round trip and fail for reasons the user does not control, which is exactly why they have a user-facing schedule.
- **Decision:** A commit is its own kind of background work, `VaultWorkKind::Commit`, admitted through the same per-Vault coordinator and holding the same per-Vault mutation lock, so there is still one execution lane per Vault and no second scheduler. A commit turn never opens a network connection: the managed-Git commit turn reuses the checkout a Vault already has and reports "up to date" rather than cloning one, because cloning is a network call. The watcher's existing debounce is the only rate limit on it, and it asks for a commit before it asks for an index, so a commit does not wait out a rebuild that can run for minutes. Which Vaults commit is decided by mode, not by whether they have a remote: Local history and Two-way commit, Pull-only does not because it refuses writes and must leave a folder its operator dirtied alone, and a plain local folder has no Git. Fetching, merging and pushing stay exactly where ADR-18 put them, on the Vault's configured poll interval, and a commit turn never touches that schedule. Manual sync and retry admit a commit for a Vault with no remote instead of refusing it; the refusal narrows to a Vault with no Git at all. Because every way a commit can fail is non-retryable and needs a person, a failed commit turn suppresses further *automatic* commits for that Vault for five minutes, coalescing whatever changes arrive meanwhile into one attempt when the window closes; a success or a manual commit clears it. The trigger is not configurable and gets no setting (ADR-14): committing promptly is the behaviour, not a preference.
- **Consequences:** A Vault's history is now as current as its last save rather than as its last restart, and the write summaries #249 introduced reach the commit that records them instead of ageing out of a bounded batch. The cost is more commits: a Local-history Vault that used to get one commit per process now gets one per burst of writing, which is the point but is also a bigger history. One status field, `git`, now answers for two operations, so a commit that succeeds on a Vault whose remote sync is failing clears that failure's status until the next scheduled sync republishes it; the alternative, a commit that can never clear a status it can set, was judged the worse lie. Two-way now commits at two different times for two different reasons, which is one more thing to hold in mind when reading a Two-way Vault's history. And the boundary has to be defended: any future work that adds a fetch, a merge or a push to the commit path breaks the decision, which is why the tests assert the remote is untouched from the remote's own side rather than by inspecting the code path.
- **Evidence:** `src/vault_work.rs` (`VaultWorkKind::Commit`); `src/vault_executor.rs` (`dispatch_commit_turn`, `plan_commit_turn`, `finish_commit_turn`, `run_planned_turn`); `src/git/managed_task.rs` (`run_managed_git_commit_turn`, `run_existing_git_commit_turn`); `src/git/managed_sync.rs` (`commit_managed_checkout`, `open_commit_repository`); `src/git/managed_checkout.rs` (`reuse_existing_checkout`); `src/git/commit_cooldown.rs`; `src/server.rs` (`forward_vault_change_intent`, `request_commit_for_change`); `src/vault_management.rs` (`managed_git_control`); `src/vault_runtime.rs` (`VaultCapabilities::commit`/`sync`); issue #267.

## ADR-24 — A slug folds European letters to ASCII and keeps every other script

- **Status:** Accepted
- **Context:** A note is addressed by a slug derived from its filename stem, and one function derived it by keeping ASCII letters and digits, mapping space, `-` and `_` to a dash, and silently discarding every other character. Discarding is not folding, so `Café` addressed as `caf` and `Veá` as `ve`: correcting a title's spelling to add an accent moved the note's address, which is how #306 was found. Two consequences followed from the same line. A title written with a combining accent rather than a precomposed letter kept its base letter and so produced a *different* address than the visually identical precomposed form, making a note's address depend on which machine created the file. And a title with no ASCII letters at all produced an empty slug, for which the indexer substitutes `untitled` and then `untitled-2`, `untitled-3` by directory-walk order, so a Vault written in Cyrillic, Greek or any CJK script has no stable addresses at all: adding one note can move every other note's address. A survey of every Vault in this project plus the operator's own (1223 notes) found 20 addresses that the fix moves, all of them accented Latin, no non-Latin script in any filename, and no note currently living at `untitled`. So the non-Latin half of this record is insurance and the folding half is the repair. Two alternatives were live. Romanising every script phonetically (`資料` to `zi-liao`) addresses everything in ASCII but needs a large lookup table as a new dependency and cannot tell languages apart, so it would spell a Japanese word the Chinese way. Keeping accents in the slug (`Café` to `café`) needs nothing new but fails the reporting case outright: it yields `veá`, which is still not the `vea` the note had before its rename. The third force is internal contradiction. `src/vault/layers.rs` already decided that layer names are Unicode, with a comment naming `sources-privées` and `資料` as valid, so slugs discarding both was the odd rule out.
- **Decision:** A slug normalises the title, strips the combining marks that sit on an ASCII letter so an accented Latin letter folds to its base letter, keeps a mark that belongs to a letter held in its own script because dropping a Devanagari virama rewrites the word it is in, maps the European letters that carry a settled conventional spelling through a short explicit table (`ß` to `ss`, `ø` to `o`, `æ` to `ae`, `œ` to `oe`, `ł` to `l`, `đ`/`ð` to `d`, `þ` to `th`), and keeps letters and digits from every other writing system unchanged. Stated as one sentence: European languages give a plain ASCII address, every other script keeps its own letters. No script is ever romanised phonetically and no character is discarded for being non-ASCII; only marks, punctuation and symbols are. The rule has two implementations, the Rust slug and the TypeScript heading anchor the browser clicks, and they carry the same table and must be changed together. The empty-result fallbacks stay, because a title of pure punctuation or emoji still reaches them. Old slugs are not kept alive: the 20 moved addresses return `note_not_found`, and the alternative, an index of what the discarding rule would have produced consulted on a miss, was rejected because it makes the defect a permanently supported way to address a note and invents a collision question between a legacy address and some future note's real one.
- **Consequences:** Twenty addresses move once, from wrong to right, and are stable afterwards; they are listed in the changelog so an operator can check anything they handed out. Nothing has to be rebuilt to get there, because the indexer already compares each path's cached slug against the one it just computed and replaces the row when they differ, so the first index turn after the upgrade reprocesses only the affected notes. The combining-versus-precomposed split closes as a side effect, since both forms now fold to the same slug; the title-matching path itself still does not normalise, which is left alone deliberately. The costs are a hand-maintained table that a future European letter may need adding to, and a rule living in two languages that a reviewer has to keep in step: a change to one implementation without the other silently splits a note's address from its own headings' addresses. The heading anchor the cache stores is computed by the Rust implementation and read by nothing; it starts holding correct values for free and its removal is deliberately not bundled here, because dropping a column bumps the cache schema, and a schema bump wipes and re-embeds every note (ADR-01), which is the wrong price for deleting something unread.
- **Evidence:** `src/vault/paths.rs` (`slugify`); `frontend/src/lib/noteHeadings.ts` (`slugifyHeading`, `assignHeadingId`); `src/vault/index.rs` and `src/vault/write/notes.rs` (the `untitled` fallback and slug assignment); `src/cache/populate.rs` (the cached-path-to-slug comparison that makes the change self-healing); `src/cache/parse.rs` (`extract_headings`, the unread anchor); `src/vault/layers.rs` (the Unicode layer-name precedent this record aligns with); issue #306.

## ADR-25 — A Vault's write exclusion outlives the control block that carries it

- **Status:** Accepted (refines ADR-18 and ADR-03; supersedes nothing)
- **Context:** Every Vault has one mutation lock, and three separate guarantees rest on it being *one*: optimistic concurrency on the shared write path (ADR-03), a Git turn's checkout reset never landing under a write (ADR-18), and an Index turn labelling a publication Fresh only when nothing mutated during its read phase. The lock was a field on `VaultControlBlock`, and `reconcile()` builds a replacement control block for any Vault whose `VaultDefinition` is not equal to the live one. A rename, a new poll interval, an edited exclude pattern, a re-entered credential — each of those published a block holding a brand-new, unlocked mutex, visible to the write path the instant the state lock dropped, while the retiring block's in-flight write, Git turn or Index read phase still held the old one. The retirement path waited for that old guard, but waiting retires bookkeeping; it does not stop the new block admitting a writer. For the length of that window one directory had two independent mutexes and none of the three guarantees held. The MCP `batch` tool had the matching problem from the other side. It is the only caller that holds more than one Vault's lock at once, and it took them lazily, in whatever order the caller's items named Vaults, holding each to the end of the call. Two concurrent batches naming two Vaults in opposite orders wedged both Vaults' entire write paths until the process was restarted, silently. And because it re-resolved the control block per item, a definition edit mid-batch handed later items the replacement block's different mutex, so they wrote with no live lock at all (#321, from the 2026-09-18 pre-release audit).
- **Decision:** A Vault's write exclusion is a value with its own lifetime, not a field whose lifetime is the control block's. `VaultWriteExclusion` holds the mutation mutex, the mutation generation counter read under it, and the refresh mutex, and a control block built to replace a live one inherits it — the same way the Git status and the pending write ledger already travel across that rotation. A definition edit therefore rotates the definition and nothing else; the only ways to get a fresh exclusion are a genuinely new Vault and one coming back from disabled, both of which have no live work to exclude. Where more than one Vault's lock is needed at once, acquisition is **ordered by Vault ID and complete before any work runs**, never lazy and never in caller order. `batch` pre-scans its items for the Vaults they write, sorts, and acquires up front. There is deliberately no acquisition timeout: a total order over the only multi-lock holder makes a cycle impossible, while a batch may legitimately wait minutes behind a Git turn's network work, and a timeout would convert that wait into a spurious failure. A holder that must keep working across a possible reconcile identifies the exclusion it holds by pointer, not by Vault: when the resolved block is no longer live — whether it was retired while the holder queued for the lock or after the lock was taken — the holder resolves the replacement and continues only when that replacement shares the exclusion, and otherwise refuses with a structured error rather than writing unlocked.
- **Consequences:** Editing a Vault's settings is no longer a way to break write exclusion on it, which is the point, and the mutation generation an Index turn took before an edit stays comparable with the one it takes after, so a turn spanning an edit still reports its freshness honestly. Reconcile's boundary wait can now be delayed by a write admitted *after* the edit, because both queue on one mutex; that is the correct behaviour and is bounded by one mutation. Two overlapping lifecycles for one Vault now wait at that same lock rather than at two, so they serialize where they used to pass through each other — fine for the polled tasks the process actually runs them as, and a trap for a test that parks one lifecycle mid-wait and then drives another. A Vault whose path changes while it stays enabled keeps one exclusion across two directories for the length of that reconcile, which is conservative rather than wrong. `batch` now blocks on every Vault it will write before running its first item, including the read items ahead of them, and a Vault it could not resolve during that pre-scan is refused for the whole call, reporting the reason the pre-scan recorded, rather than written unlocked — both are visible behaviour changes, and both are the safe direction. The rule a future change has to respect is the narrow one: nothing may construct a mutation lock for a Vault that already has one, and nothing may take two Vaults' locks in an order it chose for itself.
- **Evidence:** `src/vault_runtime.rs` (`VaultWriteExclusion`, `CarriedOverState`, `VaultControlBlock::activate`, `reconcile`, `write_exclusion`); `src/mcp/tools/batch.rs` (`lock_touched_vaults`, `lock_one_vault`, `dispatch_one`); `src/mcp/tools/write.rs` (`scoped_vault_by_id`, `shares_write_exclusion`, `exclusion_lost_error`); the tests named for this behaviour in `src/vault_runtime/tests.rs` and in `src/mcp/routes.rs`'s test module, which is where `batch`'s end-to-end locking tests live — `src/mcp/tools/batch.rs`'s own `mod tests` covers only the op-set invariants; ADR-03 for the shared write path this protects, ADR-18 for the Git turn that holds the same lock, and issue #96 for the defect this stops being reintroduced. This record covers lock lifetime and acquisition order only. Issue #321 also bound a planned text rewrite's commit-time CAS to the hash read when the plan was built (`TextRewrite::original_hash` in `src/vault/write/types.rs`, `apply_rewrites_with_before_commit` in `src/vault/write/fs_ops.rs`, `RewriteBase`/`planned_base`/`merge_rewrites` in `src/vault/write/rewrites.rs`, and the producers in `src/vault/write/assets.rs` and `src/vault/write/tags.rs`); that invariant is recorded in the module map under "Vault-qualified mutation core" rather than here, because it is about what a write checks against, not about which lock it holds.

## ADR-26 — A write commits atomically where the filesystem can, and says so where it cannot

- **Status:** Accepted (refines ADR-03; supersedes nothing)
- **Context:** Hatchdoor 2.5.0 replaced the write layer's check-then-rename commit with `renameat2(RENAME_EXCHANGE)`. The gain is real: the exchange puts the new bytes in place and hands back the bytes it displaced under a private name, so a save made in another editor between the read and the commit is detected and put back instead of being overwritten. What the change assumed is that the flag is always there. It is not. `renameat2` has been in Linux since 3.15, but each filesystem implements its flags separately, and OpenZFS before 2.2.0 rejects any non-zero flag with `EINVAL`, as does every FUSE filesystem. Ubuntu 22.04's default kernel ships OpenZFS 2.1.5, which makes this an ordinary self-hosted configuration rather than an exotic one. On such a host every write with a commit point failed: editing, appending, replacing a section, updating frontmatter, and every move, which is to say rename, archive, delete and the attachment operations too, since a move commits with the same exchange. Creating a note still worked, because it passes no expected hash and takes the plain-rename branch, so the instance looked healthy. Managed Git provisioning failed for the same reason at a different flag, `RENAME_NOREPLACE`, and threw the errno away entirely. Nothing was logged on any of these paths, so the whole failure reached the operator as `write_failed: Invalid argument (os error 22)` in their MCP client, and finding it took an strace of the running container (#345). Two things were wrong, and they are independent: the write path had no path that works where the flag does not, and the software said nothing about either the failure or the reason.
- **Decision:** Writing is not conditional on the flag. Where a flagged rename reports that the filesystem cannot do the flag, the operation falls back to the shape it had before 2.5.0: verify the precondition, then rename. Every precondition still holds and every refusal keeps its code and its wording, so a stale expected content hash is still `write_conflict` with the same sentence and an occupied move destination is still a conflict. The single thing lost is atomicity against a writer outside Hatchdoor, and losing it is preferred to refusing to write at all. The fallback is keyed on a **probe**, never on the errno alone: `EINVAL` is equally what the kernel returns for genuine misuse of the call, so a blanket errno fallback would silently convert a future bug of that kind into non-atomic writes. The probe performs the real operation on dot-prefixed scratch names in the directory in question, cleans up on every path, caches its verdict per filesystem, and never asks what the filesystem is called or which version it is. It answers in three states, and the third matters: a directory the probe cannot use, because it is missing or read-only, is `Undetermined`, never `Unsupported`, because a Vault that cannot be written has its own reason to report and must not be blamed on the filesystem. Since the verdict is cached per filesystem rather than per directory, a read-only Vault on a filesystem already known to be capable answers `Supported`, which is the honest answer to a question about the filesystem. The degradation is then stated rather than implied, in three places that serve three different readers. One log line per Vault when its runtime is established names the mechanism and what it costs, not the errno. An I/O write failure that reaches a client is logged server-side, which is the narrow fix for the silence and is independent of the fallback. And `WriteCapabilities`, with its HTTP and frontend types, carries the answer so the Vault can tell the person using it that their saves are protected less well than usual. The managed Git checkout's install gets the same treatment at its own flag, and its error stops discarding the errno.
- **Consequences:** A Vault on OpenZFS 2.1.x, on FUSE, or on anything else without flag support is writable again, which is the point, and it is writable with a named, visible weakness rather than a hidden one. The weakness is genuine: between the check and the rename there is a window in which a save made in another editor is overwritten instead of refused, and on the move path there is a comparable instant where the destination name is reserved by nothing. Hatchdoor's own concurrent writes are unaffected either way, because the per-Vault mutation lock serialises them and always did; the exchange only ever guarded against writers outside the process. The probe is one more thing that touches a Vault directory, so it is written to leave nothing behind and to answer `Undetermined` rather than guess. Caching per filesystem means a verdict is not re-derived per write, and it also means a filesystem remounted with different capabilities inside one process lifetime keeps the old verdict until restart, which is accepted. The rule a future change has to respect is narrow and easy to break by accident: a new commit point may use a `renameat2` flag, but it must ask the probe what to do when the flag is refused, and it must not read a bare `EINVAL` as an answer.
- **Evidence:** `src/rename_flags.rs` (`support`, `flag_unavailable`, `probe`, and the test-only override the regression tests drive); `src/vault/write/fs_ops.rs` (`exchange_unavailable`, `commit_checked_without_exchange`, `move_checked_without_exchange`, and the three exchange call sites that branch to them); `src/vault_mutation.rs` (`WriteCapabilities::atomic_compare_and_swap` and the `tracing` call on `WriteError::Io`); `src/vault_runtime.rs` (`report_compare_and_swap_support`); `src/handlers/vault_write.rs` and `frontend/src/types.ts` for the reported capability; `src/git/managed_checkout.rs` (`atomic_install`, `install_without_noreplace`, `AtomicInstallFailed`); issue #345; ADR-03 for the shared write path this constrains, and ADR-01 for why the file's own bytes are what the guarantee is about.

## ADR-27 — An agent moves attachment bytes through a transfer link, not the MCP token

- **Status:** Superseded by ADR-32, which restates every rule below and widens upload links to notes (refines ADR-08 and ADR-09)
- **Context:** `get_attachment` answers by default with a relative `download_url` that works only when the request carries this MCP session's bearer token in an `Authorization` header, and the recommended upload method is a multipart `POST` authenticated the same way. Both assume the caller holds the token and knows the server's address. An agent running inside an MCP client holds neither: the client keeps the endpoint and the token in its own configuration and never passes them to the model. The fallback, base64 inside the tool call, puts the whole file through the model's context, and Claude Code truncates tool output at 25,000 tokens by default, so it fails for any ordinary PDF. On 2026-09-18 an agent asked a question answered by a 1.5 MB appliance manual in the Vault and had no route to it (#310). Handing the agent the token is not an answer: it grants write access to every Vault and would sit in shell commands and transcripts, and Claude Code's own classifier refused the attempt. Three alternatives were weighed and rejected. A local helper command that reads the token itself works only where it is installed and still reads a credential file. Paging base64 through the conversation costs hundreds of thousands of tokens per file and cannot upload. Extracting a PDF's text answers one question type and leaves every other file type, and uploads, where they were.
- **Decision:** An authenticated MCP call may mint a **transfer link**: an absolute URL carrying its own credential, good for one attachment download or one upload to one target, with no MCP token needed to redeem it. It is a new kind of credential, strictly narrower than the token that minted it, and this record is the deliberate exception to ADR-08 and ADR-09's rule that every request carries a bearer token. `get_attachment` with `encoding: "url"`, its default, returns a download transfer link; a new `create_upload_link` tool mints an upload link, and `get_attachment_import_config` recommends it. The bearer-header route stays and keeps working unchanged for clients that hold the token.
  - *Scope.* A download link names one Vault and one relative path and is refused for any other. An upload link names one Vault, one target relative path, and whether replacing an existing file is allowed, all fixed when it is minted; minting refuses at once when the target exists and replacing was not allowed, and redemption checks again.
  - *Lifetime.* Every link expires five minutes after minting, checked when a transfer starts so a slow upload that started in time is not cut off. The length is fixed and has no setting. A download link may be redeemed any number of times until it expires; an upload link is redeemed once.
  - *Revocation.* Links are signed with a random key held only in memory, never written to disk, and replaced whenever the MCP token changes. Every live link therefore dies on expiry, on restart, and on an MCP token change. Redemption also re-reads the live configuration per request, as the bearer route does, so disabling MCP refuses every link at once and disabling MCP write mode refuses every upload link.
  - *Allowance.* A link is a cheaper transport, not a larger allowance, which is the rule #176 set for the bearer URL. A download redeemed through a link spends the same tool-call quota and concurrency budget and stops at the same `HATCHDOOR_MCP_MAX_BASE64_BYTES` ceiling as a read over `/mcp`. An upload keeps `HATCHDOOR_MAX_ATTACHMENT_BYTES`. A link obeys the same browse-surface and layer visibility as `get_attachment`.
  - *Address.* The absolute URL uses a new optional public-address setting when one is configured, settable from the environment as well as Settings (ADR-14), and otherwise the scheme, host and port the minting MCP request arrived on. The setting exists for deployments behind a proxy or HTTPS front end, where the arriving request does not show the address clients use.
  - *Secrecy.* A link's credential is redacted from logs and trace spans like any other token (ADR-08).
- **Consequences:** An agent with no token in its context can fetch an attachment to local disk and upload a local file from a tool response alone, in any MCP client that can make an HTTP request. A leaked link exposes one file, or one upload slot, for at most five minutes, where a leaked token exposed every Vault until rotated. The costs: the server now mints and verifies a credential of its own, which is new security-relevant code; a restart or token rotation breaks links an agent is about to use, so it has to ask again; and when the address is inferred from the arriving request behind a proxy that rewrites it, links point at an address the agent cannot reach until the operator sets the public address. The inference is not a security hole, because the link goes back to the same caller who sent that address, but it is a correctness hole with a one-field remedy. Any future change that lets a link name more than one file, outlive its key, or skip the quota breaks this decision.
- **Evidence:** issue #310 (the failure and the design); #176 for the bearer URL and the "cheaper transport, not a larger allowance" rule this keeps; `src/auth.rs` (`require_web_or_live_mcp_read_token`, `require_web_or_live_mcp_token`, the guards a link must not weaken); `get_attachment` and `get_attachment_import_config` in the MCP read tools.

## ADR-28 — A note link is a wikilink or a Markdown link to a `.md` path, and both count

- **Status:** Accepted (supersedes nothing; widens what the link graph records)
- **Context:** Hatchdoor has only ever understood one way of linking notes, the wikilink `[[Title]]`. Obsidian and a handful of other tools write that form, but it is not Markdown, and every other Markdown tool writes a note link as `[text](path/To%20Note.md)`. Obsidian itself writes that form when its "Use [[Wikilinks]]" setting is off, and Notion's Markdown export writes it too. In Hatchdoor such a link rendered as a clickable anchor to a URL no route answers, and it was absent from backlinks, the Links panel, the graph, statistics and the agent link tools, so a vault written this way looked unlinked and navigated nowhere (#293). The reason for fixing it is a product one: Hatchdoor is meant to serve Markdown vaults whichever editor wrote them, and a vault that only works if its links use one tool's syntax is not that. The hard part is the link graph. Backlink counts and graph edges are things people and agents already read, and counting a second link form moves those numbers for any existing vault that happens to contain one.
- **Decision:** A **note link** is either a wikilink or a Markdown link whose target, with any `#anchor` removed, ends in `.md`. Nothing else is a note link: a Markdown link to any other extension or to an external URL keeps its current meaning, and an image-syntax link to a `.md` file is left alone. Both forms are equal everywhere a note link is read or written.
  1. *Recognition.* All three Markdown spellings count: inline `[t](p.md)`, angle-bracketed `[t](<p.md>)`, and reference-style `[t][r]` with a `[r]: p.md` definition. Links inside fenced code and inline code are skipped, as wikilinks are. Links never cross Vaults.
  2. *Resolution.* A Markdown target is a path, not a title, so it is resolved by the ladder attachments already use (`VaultIndex::resolve_asset`): a leading `/` is Vault-root-relative, then relative to the linking note's folder, then as written from the Vault root, then, for a bare filename only, by name with the nearest match winning. It is deliberately not resolved by the wikilink rule, whose last-segment fallback would send `../a/Plan.md` to whichever note titled Plan came first when two exist. Percent-escapes are decoded where `%` is followed by two hex digits; any other `%` is literal.
  3. *Counting.* Markdown note links feed the same link records as wikilinks: outgoing links, backlinks, the Links panel, the graph, link statistics and the MCP link tools.
  4. *Rendering.* A resolved link navigates in-app like a wikilink, carrying a `#heading` through with the same heading-slug rule; an unresolved one renders as the same broken-link affordance a missing wikilink gets.
  5. *Rewriting.* Renaming or moving a note retargets Markdown links to it, keeping the author's form (relative stays relative, root-anchored stays root-anchored) and never touching the link text. Moving the note that *contains* Markdown links repoints them from its new folder, as its attachment references already are (#225). Deleting a note removes the link and keeps its text, because a Markdown link's text is the author's prose rather than the target's name. When Hatchdoor writes a path it encodes only what would break the link: whitespace and control characters, `%`, `#`, and brackets or parentheses.
- **Consequences:** A vault written with Markdown links navigates, counts and survives reorganisation the way a wikilink vault always has, which is the point. The visible cost is that backlink counts, graph edges and link statistics rise for any existing vault that already contains Markdown links to `.md` files; that is the numbers becoming true rather than changing meaning, and there is no switch to keep the old count. A link written without the `.md` extension stays unrecognised, the price of never guessing whether a target names a note or an attachment. Two resolution rules now coexist, title-based for wikilinks and path-based for Markdown links, and a change to one must not be copied to the other on the assumption they are the same. Every rewriter in the write path now has two syntaxes to keep in step, which is the most likely place for this to regress. Hatchdoor still *writes* new links as wikilinks; making it write in a vault's own style is a separate decision, not taken here.
- **Evidence:** issue #293 (the failure, the triage decisions and the agent brief) and #302 for the unmatched-address pane it exposed; `src/vault/links.rs` (`extract_wikilink_targets`, `resolve_target_slug`); `src/vault/index.rs` (`resolve_asset`, the ladder reused here); `src/vault/paths.rs` (`normalize_link_target`); `src/vault/write/rewrites.rs` and `src/vault/write/assets.rs` for the rename, move and delete rewriters; `frontend/src/components/note-page/wikilinks.ts` and `renderers.tsx` for rendering; the **Note link** entry in `CONTEXT.md`.

## ADR-29 — A note is charted by its created date, and a date the author wrote beats any the machine infers

- **Status:** Accepted (applies ADR-01 to note dates; supersedes nothing)
- **Context:** The Stats page's six-month chart counted notes by file modification time. That clock does not survive the things a Vault routinely goes through. Git stores no modification times, so a clone, a restored container or a re-provisioned host stamps every file with the moment of checkout: a repository with three years of history came out with all 113 files dated to the same minute. A bulk rename stamped every note that linked to a renamed one until #299 put their times back, and #299 cannot help a clone. On the maintainer's 625-note Vault the chart read 630 notes in September and single digits in every other month. The real dates were in the repository the whole time, and many notes also carry a `created` property the author wrote. Four sources were measured on that Vault for the same chart (#300): modification time, the `created` property, the commit that first added each note, and lines written per month. The obvious git analogue of modification time, the last commit that changed a note, was measured too and rejected. It still put 717 notes in September, because a link rewrite after a rename is a real content change as far as git knows, and Hatchdoor commits those rewrites in the same automatic commit as real edits, under the same author, so no filter can separate them.
- **Decision:** The chart counts notes by **created date** (`CONTEXT.md`), the month a note first came into existence, which no rename, move, edit, clone or restore can move. Each note's created date is resolved in a fixed order. First, its `created` property when it reads as a date: a date the author wrote is more deliberate than any the machine infers, and it is the only source that predates the repository for notes imported into one. A stated date keeps the calendar day as written, whatever zone it names, because that is the day the author meant. Second, for a Git-backed Vault, the author date of the commit that first added the note, following renames forward through the whole repository rather than only the Vault's folder, so a note moved in from elsewhere keeps its date. A note is the same note across a commit only when git's rename detection pairs the two paths; a note deleted and recreated, or a copy, is new. Third, the file's modification time, which is all a plain folder has. A shallow repository contributes nothing for the notes its graft point introduced, rather than dating them all to the graft. History is walked once per Vault on a background thread, started when the Vault's runtime comes up, held in memory with the commit it describes, and extended by only the new commits when the branch moves forward; a stats read waits at most two seconds for a walk in progress and never walks itself. A walk made while the repository was shallow is never extended, so fetching the missing history dates what it could not. A note one branch deletes and a merge keeps, or that a merge brings back, keeps its date, because it never stopped existing on the branch that won; the tree at the walked commit decides which notes exist. When git could not date a note that it should have, because the history is shallow, unreadable, or still being read, the stats response says so and the page shows a one-line notice under the chart. Everything that asks what changed recently (the week and month lists, the recently changed panel, `recently_modified`) stays on modification time, which #299 keeps honest for that question. The chart's wire field is renamed from `modified_count` to `created_count`, with no alias.
- **Consequences:** The chart survives a clone, and a vault's history reads the way it was written. It now answers "what did I start" rather than "what did I touch", so a month spent revising old notes looks quiet; a volume chart would answer the other question and is a separate decision. A plain folder without `created` properties is no better off than before, and the notice deliberately does not fire for it, because nothing is missing that could be had. The cache is memory only, so every restart walks each Git-backed Vault's history again, and a stats read that arrives before a long walk finishes answers with the notice while the page asks again, up to twenty times. That is accepted in exchange for leaving the index build and its schema alone: the walk is disposable and rebuilds from the repository, as ADR-01 asks of every derived read. The rename of `modified_count` breaks any script reading the old name, which a single-user self-hosted API can afford and a misleading name cannot. A future change must not chart by modification time or by last change in git, must not let git or the file override a `created` property, and must not walk history on the request path.
- **Evidence:** issue #300 (the measurements and the triage decisions); #298 for the calendar window this feeds and #299 for the modification-time protection the recent lists rely on; `src/git/note_history.rs` (the walk and its cache); `src/vault_read.rs` (`statistics_detail`, `created_date`, `activity_window`); `src/api_types.rs` (`MonthActivity`, `CreatedDateStatus`); `frontend/src/components/StatsPage.tsx`.

## ADR-30 — A sync conflict is resolved on the Git host, through a recovery branch Hatchdoor publishes on request

- **Status:** Accepted (refines ADR-18; supersedes nothing, and every ADR-10 safety decision ADR-18 restates stays in force)
- **Context:** When a two-way Git turn cannot merge the remote into the local branch, `abort_merge` restores the checkout to the local commit, reports `managed_git_conflict` with the conflicting paths, and keeps local editing and local commits going. That is safe, and it leaves Hatchdoor's side of the conflict in exactly one place: the checkout on the server. A managed checkout lives under the instance state directory, inside a distroless image with no shell and no Git, so the only documented recovery was to reach the mounted volume from the host and run Git there as the image's user. An operator who resolves conflicts on their Git host, or who has no host access at all, could not see Hatchdoor's side, let alone merge it. ADR-18 also says a Git turn pushes the one configured branch and nothing else, so a fix that pushes anything more has to be recorded rather than slipped in (#80, triaged 2026-10-01).
- **Decision:** An operator can ask Hatchdoor to publish its side of a conflict to a **recovery branch** (`CONTEXT.md`) and resolve it on the Git host like any other branch. The branch is named `hatchdoor-recovery/<configured branch>/<vault id>`. The immutable Vault ID keeps it unique when several Vaults, or several Hatchdoor instances, share one repository, and keeps it stable across a Vault rename. Publishing happens only on an explicit request, never as a side effect of a failed sync: from the Vault's page, the matching HTTP route, and an MCP tool that is gated on write mode like `sync_vault` and is not batchable. It is offered for any Vault in two-way mode, managed or existing checkout, while its Git status reports a conflict. Pull-only Vaults never push and cannot reach this state. A request is admitted through the work coordinator as a Git turn of its own, so it holds the Vault's mutation lock and never overlaps a sync or commit turn, and it reports its outcome through the Vault's status rather than on the request. The push is a fast-forward of the recovery branch to the local head and nothing else. It never force-pushes, never touches the configured branch, and never deletes a remote branch, including the recovery branch after the conflict is gone. When the remote's recovery branch holds commits the local head does not, because someone started resolving on it, the push is refused and the status says so; the refusal and any rejection by the remote (a token without rights to create branches, a hook) leave the Vault's conflict status as it was. Nothing new is needed to resume. The scheduler keeps trying on the Vault's interval after a conflict, and the first turn that finds the configured branch containing the resolved history merges cleanly and clears the failure. Notes listed in the conflict stay editable, and the note editor warns on them, since an edit made before the fix lands can conflict again on the same lines.
- **Consequences:** A conflict becomes something the operator fixes with their usual Git host, their usual client, or an agent, with no access to the server. Hatchdoor now writes to a second branch on the remote, which a restrictive token or branch rule can refuse; that is reported, not worked around. A leftover recovery branch stays on the remote until someone deletes it, and the next conflict reuses it: its old head is already part of the configured branch, so the next publish is a fast-forward too. Edits made after a publish are not on the branch until the operator publishes again, which the status makes visible by naming the published commit. A future change must not publish without a request, must not rewrite or delete a remote branch, and must not run the publish outside a Git turn.
- **Evidence:** issue #80 and its triage notes; `src/git/managed_sync.rs` (`abort_merge`, `push`, the refspec that names only the configured branch today); `src/git/managed_task.rs` (`classify_sync_error`, the scheduler's retry after a non-retryable failure); ADR-18 for the Git turn this adds a kind to, ADR-25 for the lock it holds. Implementation: `src/git/managed_sync.rs` (`publish_recovery_branch`, `recovery_branch_name`, `push_refspec`, `ManagedSyncError::RecoveryDiverged`/`RecoveryRejected`); `src/git/managed_task.rs` (`run_managed_recovery_turn`, `run_existing_git_recovery_turn`, `CONFLICT_CODE`); `src/vault_work.rs` (`VaultWorkKind::Recovery`); `src/vault_executor.rs` (`dispatch_recovery_turn`, `plan_recovery_turn`, `finish_recovery_turn`, and the clearing in `publish_managed_git_turn_outcome`); `src/vault_runtime.rs` (`RecoveryBranchStatus`, `VaultCapabilities::publish_recovery`); `src/vault_management.rs` (`publish_recovery`); `POST /api/v1/vaults/{vault_id}/recovery-branch` and the MCP tool `publish_recovery_branch`; `frontend/src/features/settings/VaultSettingsIndex.tsx` (`RecoveryBranchPanel`) and `NotePage`'s `SyncConflictNotice`. One implementation choice the decision above does not name: admission refuses an ineligible Vault with the existing `capability_unavailable` code rather than a code of its own, so clients handle it like every other refused Vault control.

## ADR-31 — Git work never waits behind another Vault's indexing

- **Status:** Accepted. Supersedes the clause of ADR-18 "scheduled through the coordinator with no second execution lane" and the clause of ADR-23 "so there is still one execution lane per Vault and no second scheduler". Every other ADR-18 and ADR-23 decision, and every ADR-10 safety decision ADR-18 restates, remains in force. The words "exactly as today" in decision 1 are superseded by ADR-35: indexing keeps one lane, but an Index turn may now pause and rejoin it.
- **Context:** All expensive background work runs through one instance-wide FIFO worker that finishes each turn before it starts the next: Index turns with their embedding, Git sync turns, commit turns, recovery turns and repair. That was chosen for simplicity when the collection runtime landed (#70), and #81 was filed to revisit it once a measurement showed the delay mattered. The measurement, taken during the triage of #81 on 2026-10-01: a local instance on a 4-core VM served two Vaults, a 759-note Vault (7 MB of Markdown, 4,092 chunks) being indexed for the first time and a 49-note Local history Vault. The large Vault's Index turn read its notes in 1.5 minutes and then estimated about 2 hours of embedding at roughly 30 chunks a minute. An edit saved to the small Vault was still uncommitted 33 minutes later, when the run was stopped; on that rate it would have waited over 2 hours. Its own first Index turn waited the same way, so it could not be searched either. Nothing in either Vault's status said why. Embedding speed varies with hardware, but the shape does not: every other Vault waits for the full length of the slowest Index turn, and adding a large Vault or changing the search model starts one. ADR-23 made commits run on every burst of writing rather than once a day, so this wait now lands on routine saves. A Vault's history and its remote copy fall behind silently, which costs data safety; a slow search costs only time, and the user can see it.
- **Decision:** Git work and indexing are admitted separately.
  1. **Indexing keeps one instance-wide lane.** Index and Repair turns run one at a time, FIFO, across all Vaults, exactly as today. Indexing is CPU-bound and the embedder already serializes inference, so a second indexing lane would buy nothing without a larger change.
  2. **Git work runs per Vault.** Git sync, Commit and Recovery turns for one Vault never wait for any Index turn, and never wait for another Vault's Git work. A Vault's own Git turns still run one at a time, in FIFO order, with today's coalescing.
  3. **At most four Vaults run Git work at once.** The cap is a fixed constant, not a setting (ADR-14). Git work is network- and disk-bound, so a few side by side costs little, and the cap stops a burst of due syncs, or several Git Vaults added together, from swamping a small machine. A Vault beyond the cap waits for a slot, not for indexing.
  4. **The same-Vault guard is the existing write lock.** No new working-tree gate is added. An Index turn holds the Vault's mutation lock only while it reads Markdown, and a sync turn holds it for its whole blocking duration and counts as a mutation (ADR-25). On one Vault, a sync therefore cannot rewrite notes while an Index turn is reading them, and an Index turn whose embedding overlapped a sync publishes its generation Stale; the sync's success requests one coalesced follow-up Index turn, which reuses the vectors already embedded. A sync waits at most for its own Vault's read phase, never for embedding.
  5. **Lifecycle waits for both.** Disabling, removing, reconciling or shutting down a Vault stops new work in both places, discards queued work in both, and waits for the safe boundary of whatever that Vault has running in either. There is still no forced cancellation and no generic timeout.
- **Consequences:** The promise a multi-Vault user gets is narrow and checkable: saving and syncing one Vault never stalls because another is indexing. Search fairness is not part of it. A small Vault's first Index turn can still wait hours behind a large one's embedding; that is tracked separately, together with the finding that an interrupted Index turn discards every vector it computed, because a partial build lives in an in-memory candidate cache that is published only on completion. A sync on a Vault mid read phase now waits for that read phase (about a minute for a large Vault on slow hardware), which is the one same-Vault delay accepted in exchange for not splitting today's sync into separately locked phases. Lock ordering stays simple because no Git turn or Index turn ever takes two Vaults' locks; ADR-25's sorted acquisition remains the only multi-lock rule. A future change that wants fetch and push to run during a read phase, a second indexing lane, or a configurable cap needs its own record.
- **Evidence:** issue #81 and its triage notes; issue #70 for the original single-FIFO contract. Today: `src/vault_work.rs` (`VaultWorkCoordinator`, `VaultWorkWorker::run_next`, `VaultWorkKind`); `src/vault_executor.rs` (`dispatch_vault_index_turn_with_embed_layers` takes the mutation lock for the read phase only and retakes it to publish; `run_planned_turn` holds it for a Git turn; the successful-sync path requests a follow-up Index turn); `src/vault_runtime.rs` (`acquire_mutation` counts a mutation, `blocking_retake_mutation_for_index` compares generations); `src/cache/vault_snapshots.rs` (the in-memory candidate cache and `publish_vault_candidate`); `src/embed/fastembed_embedder.rs` (inference behind one `Mutex`).

## ADR-32 — A transfer link can upload a note as well as an attachment

- **Status:** Accepted (#303). Supersedes ADR-27, whose transfer-link rules this record keeps whole and widens on the upload side to notes. ADR-27's text stays as the record of #310. Its *Address* rule is superseded by ADR-34.
- **Context:** An agent has no way to turn a Markdown file already on its disk into a note without reading it and re-emitting every byte through `create_note`. Every upload route takes images and PDFs only and creates an attachment. Retyping pays for the content twice in tokens and depends on the model transcribing it faithfully. On 2026-09-09 an import of six research files (3,459 lines, 416,264 bytes) read one of them in bounded chunks that stopped at line 594 of 599. Five items were never written, nothing errored, and the hole was found only by diffing the Vault's Git mirror against the source files (#303). ADR-27 already lets an agent send a local file with neither the token nor the model in the path, but only as an attachment. Two alternatives were rejected. A file-path argument on `create_note` cannot work, because the server cannot read the agent's disk. A separate note-upload tool would only be found after `create_upload_link`, the tool an agent holding a file already reaches for, refused the `.md` file.
- **Decision:** ADR-27's transfer link stands with every part (scope, lifetime, revocation, allowance, address, secrecy) unchanged, except that an upload link may now target a note.
  - *Note or attachment.* `create_upload_link` decides by the target. A relative path ending in `.md` mints a note upload; any other path mints an attachment upload under the existing extension list. An uploaded `.md` file is always a note and never an attachment.
  - *Same write.* A note upload is the note write `create_note` performs, with the uploaded file as its content, through the mutation core and `vault/write` (ADR-03, ADR-19). It gets the same refusals (not UTF-8, a NUL byte, a layer marker or noise path), the same line-ending and final-newline normalisation, the same quality warnings, and the same indexing and commit. Hatchdoor does not store the bytes verbatim, so one definition of a valid note holds however the note arrived.
  - *Replacing.* An upload replaces an existing note only when the link was minted with replacing allowed, as for attachments. A replacing note link also carries the note's expected content hash, fixed and signed into the link at minting. Minting refuses a replacing note link without one, and redemption refuses with the same conflict `update_note` returns when the note no longer has that hash. No link replaces a note blindly.
  - *Size.* A note upload is capped by `HATCHDOOR_MAX_ATTACHMENT_BYTES`, like every upload. There is no separate note setting.
  - *Answer.* A note upload answers with what a note write answers: the note's slug, relative path, new content hash and quality warnings, so the next replace can chain from it.
  - *Who.* This is for agents. The web UI's attachment drop keeps refusing Markdown; importing a file through the browser needs its own decision.
- **Consequences:** An agent moves an existing Markdown file into a Vault with one tool call and one HTTP request, and the content never passes through the model, so a long file cannot be cut short in transcription. A re-import cannot silently overwrite edits made since the agent last looked, at the cost of one `get_frontmatter` call to fetch the hash. An uploaded note can differ from its source in line endings and a final newline, and its warnings say so, so a byte diff against the source has to allow for both. The upload link carries one more signed field, which is security-relevant code. Any future change that lets a link replace a note without its hash, stores an uploaded note without the checks `create_note` applies, or makes a non-`.md` target a note breaks this decision.
- **Evidence:** issue #303 and its triage; ADR-27 and #310 for the transfer link; `create_note`, and `update_note` with its `expected_content_hash`, in the MCP write tools; `get_frontmatter`, which returns a note's content hash without its body; ADR-22 and #316 for why a note keeps one line-ending style.

## ADR-33 — A vault's link style is read from the vault, not set in Hatchdoor

- **Status:** Accepted, implemented in #357. Takes the decision ADR-28 left open ("Hatchdoor still *writes* new links as wikilinks").
- **Context:** Since ADR-28 Hatchdoor reads a Markdown note link as readily as a wikilink, but every link it inserts is still a wikilink: editor autocomplete inserts `[[Title]]`, and pasting, uploading or dropping a file inserts `![[path]]`. In a vault whose author chose Markdown links, usually so other tools can read it, each insert adds a link those tools cannot follow, and the vault drifts into two styles. Agents make it worse: nothing tells them a vault's style, so they write wikilinks everywhere, and in practice they write more new links than the editor does. Four ways to know a vault's style were weighed. A per-Vault setting is predictable but adds a stored field, an `edit_vault` change and a settings control, and goes stale when the author flips the switch in Obsidian. Always writing Markdown links imposes a style on every wikilink vault, which is every vault today. Counting the vault's existing links needs no setup but guesses. Obsidian already records this exact choice inside the vault, in `.obsidian/app.json` (`useMarkdownLinks`, and `newLinkFormat` for the path form), and writes a key there only once it differs from Obsidian's default.
- **Decision:** A vault's **link style** is read from the vault each time it is needed, never configured in Hatchdoor.
  1. *Style.* If the vault has Obsidian's `.obsidian/app.json`, its `useMarkdownLinks` decides, and a missing key means wikilinks, Obsidian's default, so Hatchdoor and Obsidian never add different styles to one vault. Otherwise the style is whichever form most of the vault's existing note links and attachment embeds use. No links, or an exact tie, means wikilinks.
  2. *Path form.* A Markdown link's path follows Obsidian's `newLinkFormat` when the vault has `.obsidian/app.json` (a missing key means Obsidian's default, shortest), and is relative to the linking note otherwise, the one form every Markdown tool follows.
  3. *What follows it.* Every link Hatchdoor inserts where there was none: editor autocomplete, which in Markdown style inserts `[Title](path.md)` with the note's title as the link text, and the attachment inserts (paste, upload, drop), which insert `![](path)`. One style covers note links and embeds, as Obsidian's one switch does.
  4. *Agents.* The Vault shape returned to agents and the HTTP API carries the vault's link style and path form, so an agent can write matching links. Hatchdoor never rewrites the text an agent sends into the vault's style.
- **Consequences:** A Markdown-link vault keeps one link style when edited through Hatchdoor, with nothing to configure, and an Obsidian user who flips the switch in Obsidian sees Hatchdoor follow. The cost is a guess on vaults Obsidian never opened: a vault split close to evenly between the two styles can flip as notes change, and nobody can correct a wrong guess, because there is no override. Hatchdoor now reads one file inside `.obsidian/`, which it otherwise treats as noise, and only reads it. An agent that ignores the reported style still writes wikilinks, by design. Reading, rewriting and removing existing links is unchanged and stays ADR-28's. If a vault the rule gets wrong turns up, the remedy is a per-Vault override whose default is this rule, recorded in a superseding ADR, not a change to the rule's order. Two consequences of the implementation (#357): without `.obsidian/app.json` each Vault listing walks the Vault and reads every note changed since the last listing, keeping per-note counts in memory, because the cache's link records carry no form and adding one would mean a cache rebuild; and the note page now resolves a Markdown image `![](path)` through the attachment ladder (`resolve_asset`), as it already did `![[...]]`, so the root-anchored and bare-name paths these inserts can write render. Image syntax still never counts as a note link.
- **Evidence:** issue #357 and its triage; ADR-28 and #293 for reading both forms; editor autocomplete (`applyWikilinkSelection`) and the attachment inserts (`insertAttachmentAtCaret`, `insertEmbedAt`) in the frontend; the Vault shape `list_vaults` returns; the **Link style** entry in `CONTEXT.md`.

## ADR-34 — A transfer link's address follows the proxy's forwarded headers

- **Status:** Accepted (#358). Supersedes only the *Address* rule of ADR-32 (inherited from ADR-27); every other transfer-link rule stands.
- **Context:** ADR-27 builds a transfer link on the public-address setting when one is set, and otherwise on the scheme, host and port the minting MCP request arrived on. Hatchdoor serves plain HTTP, so an arriving request is always `http`, and behind a TLS-terminating proxy every inferred link starts with `http://` even though the agent reached the server over `https://`. ADR-27 named this "a correctness hole with a one-field remedy". In practice the hole costs more than one field. On 2026-09-30 an agent fetched a PDF from an instance behind openresty with no public address set. The proxy answered the `http://` link with a 301, `curl -o`, the example the tool response itself gives, saved the 166-byte redirect page as the PDF and exited 0, and the agent noticed only when text extraction failed. A client that follows the redirect instead sends the signed link across the network in clear text first (#358). Most proxies already tell the server the client's scheme and host in `Forwarded` (RFC 7239) or `X-Forwarded-Proto` and `X-Forwarded-Host`, and Hatchdoor ignored both. The `get_attachment` description also told agents the link used "this MCP endpoint's scheme", which was never true behind a proxy.
- **Decision:** A transfer link's absolute address is chosen in this order, per minting request:
  1. The public-address setting (`HATCHDOOR_PUBLIC_URL`, **Public address** in Settings) when set. It always wins, and stays the remedy for a proxy that sends no forwarded headers or mounts Hatchdoor under a path prefix.
  2. Otherwise the request's `Forwarded` header: the `proto` and `host` parameters of its first element.
  3. Otherwise `X-Forwarded-Proto` and `X-Forwarded-Host`, each taking its first comma-separated value.
  4. Otherwise `http` and the `Host` header (or an HTTP/2 request's authority), as before.

  Scheme and host are resolved independently down that list, so a proxy that forwards only the scheme still keeps the arriving `Host`. A scheme other than `http` or `https`, or a host that does not parse as an authority or carries credentials, is ignored and the next source is used. A malformed header never fails the tool call. The headers are trusted from any sender, with no trusted-proxy list, for the reason ADR-27 already gave for `Host`: the link goes back only to the caller who sent them, so a forged header misleads nobody but the forger. Nothing else in Hatchdoor reads these headers, and this record does not make them meaningful anywhere else (origin checks, logging, rate limiting). Tool descriptions and user docs describe the address as the public address if set, else the address the client reached the server on as the proxy reports it.
- **Consequences:** An instance behind a proxy that sends the standard headers (Caddy, Traefik and Nginx Proxy Manager do by default; plain nginx and openresty need `proxy_set_header`) mints `https://` links with nothing to configure, and the silent wrong-file download goes away for it. A proxy that sends neither header, or forwards a wrong one, still produces a wrong link, and the remedy is still the public address, which the install guide now has to mention for proxied installs. Reading two more request headers is small, security-adjacent code. Any future change that lets these headers affect anything other than a transfer link's address, or lets them override a configured public address, breaks this decision.
- **Evidence:** issue #358 and its triage; ADR-27 and ADR-32 for the transfer link; `request_origin` in `src/mcp/adapter.rs`, which hardcoded `http` before #358; `McpConfig::link_base` in `src/mcp/config.rs`; the `get_attachment` tool description in `src/mcp/tools/read.rs`; RFC 7239.

## ADR-35 — A long Index turn keeps its embedding progress and takes turns with other Vaults

- **Status:** Accepted, not yet implemented (#375). Supersedes the words "exactly as today" in decision 1 of ADR-31. ADR-31's single instance-wide indexing lane, its Git lanes and every other decision stand.
- **Context:** ADR-31 freed Git work from indexing and deliberately left search fairness out. The measurement that motivated it, taken on 2026-10-01 on a 4-core VM, still applies to indexing: a 759-note Vault (4,092 chunks) indexed for the first time read its notes in 1.5 minutes and then estimated about 2 hours of embedding at roughly 30 chunks a minute, and a 49-note Vault added alongside it could be neither browsed nor searched for that whole time, because its first Index turn queued behind the large one. Two facts in the code shape the fix. First, an Index turn builds into an in-memory candidate cache, seeded from the Vault's last searchable generation and copied to disk only when the whole build finishes, so an interrupted turn discards every vector it computed: a restart at 90% of a two-hour first build starts from zero, on a single-Vault instance too. Second, two Index turns cannot embed at once: the embedder serializes inference behind one mutex, and a process-wide model-epoch lock spans a whole candidate build and publish. Three directions were weighed: saving progress alone, saving progress and slicing long turns so they yield, and running Index turns for several Vaults concurrently.
- **Decision:**
  1. **Embedding progress is saved as it is made.** Vectors an Index turn computes are written to disk in the disposable cache as the turn goes, and a later turn for the same Vault and the same search model reuses them by content, as it already reuses a published generation's vectors. A restart, a crash or a pause therefore resumes instead of starting over. Saved progress is disposable like the rest of SQLite (ADR-01): losing it costs time, never data. A search-model change discards it. Removing a Vault deletes it; disabling a Vault keeps it.
  2. **Saved progress is not searchable.** A Vault stays all-or-nothing for search: it becomes searchable only when every chunk has a vector, exactly as now, and until then a Vault that had a searchable generation keeps serving it, marked stale. A result set never silently omits the part of a Vault that has not been embedded yet.
  3. **A long Index turn takes turns.** After about five minutes of embedding, an Index turn checks whether another Vault's Index or Repair turn is queued. If one is, it stops at the next chunk boundary with its progress saved, and its Vault rejoins the back of the indexing queue; it resumes from its saved progress when its turn comes round again. If nothing is waiting it carries on without pausing, so a single-Vault instance never pays for this. The five minutes is a fixed constant, not a setting (ADR-14), and it is measured in time, not chunks, so the bound on a waiting Vault holds on any hardware. Resuming re-reads the Vault's Markdown, about 1.5 minutes for the large Vault above; that overhead is accepted while another Vault is waiting, and if it hurts the fix is a cheaper re-read, not a longer slice.
  4. **The queue stays first come, first served.** A paused Vault goes to the back, behind everything already queued, and nothing jumps ahead of anything else. One Vault embeds at a time; Index turns for several Vaults never run concurrently.
  5. **A waiting Vault says so.** A Vault's status, in the web UI and over MCP, distinguishes an Index turn that is embedding from one that is waiting for its turn. The progress percentage survives pauses and restarts, and the time estimate counts embedding time only, so a paused Vault's countdown does not look frozen.
- **Consequences:** On the measured case, the 49-note Vault becomes browsable and searchable within about five minutes of being queued instead of after two hours, and an interrupted first build loses at most the chunk in flight. The large Vault finishes later while others are waiting, by roughly a quarter on the measured hardware, and is no slower when nothing is. CPU and memory stay where they are, which matters most on the small hosts where the wait hurt most. The large Vault itself still cannot be searched until it is fully embedded; partial search was rejected because a result set that silently skips unembedded notes is wrong in a way the reader cannot see. The status change is externally observable and goes through the interface-change checklist. A change that wants partial search, concurrent embedding, a priority order, or a configurable slice needs its own record.
- **Evidence:** issue #375 and its triage; ADR-31 and issue #81 for the lanes. Today: `src/cache/vault_snapshots.rs` (`replace_vault_snapshot_with_embed_layers_and_progress` builds an in-memory candidate seeded by `seed_candidate_from_snapshot` and holds `snapshot_model_epoch` across build and publish; `publish_vault_candidate` is the only write to disk); `src/embed/fastembed_embedder.rs` (inference behind one `Mutex`); `src/vault_work.rs` (the indexing FIFO); `src/vault_runtime.rs` (`VaultRuntimeSnapshot`, `VaultPhase`, `set_indexing`); `src/startup.rs` (`IndexingProgressSnapshot`).
