# MCP conformance run — 2026-09-03 (v2.6.0 release evidence)

Clean release evidence for the **40-tool** catalogue on `development`, taken as
the pre-merge gate for the v2.6.0 release PR into `main`. Supersedes
[`./2026-08-28-mcp-capability-expansion.md`](./2026-08-28-mcp-capability-expansion.md),
which verified the same boundary at 39 tools. That run predates four MCP-facing
changes in this release, so it no longer describes the surface being shipped:

- `refresh_vault` (#228), taking the catalogue from 39 to 40.
- `get_frontmatter` gaining a non-optional `content_hash` field (#227).
- `get_tree` gaining `folder`, `max_depth` and `include_notes`, and its notes
  **dropping `vault_id`** (#192, #211) — a breaking result-shape change.
- Five note-mutation tool descriptions rewritten for the asset-travel rule
  (#231).

Procedure: [`../mcp-conformance-run.md`](../mcp-conformance-run.md).

- Runner: `@modelcontextprotocol/conformance` **0.2.0-alpha.11** via `npx -y`
  (`--version` confirmed at the start of this run), the same version the
  superseded run used, and the newest published version of any kind. Note that
  the bare unpinned package resolves to stable **0.1.16**, which has no
  `--requirements` option and cannot run the Stage B invocations; the pin is
  required, not cosmetic. The procedure's Runner section has been corrected to
  say so.
- Server: local dev build (`just dev-start`) reporting version `2.6.0`,
  `http://127.0.0.1:42824/mcp`, reached through the documented
  header-injecting proxy on `127.0.0.1:42999`. The proxy's target and token
  were verified against this build before the suite was invoked.
- Baseline: [`../conformance-baseline.yml`](../conformance-baseline.yml),
  reviewed for this run and **unchanged** — no entry went stale (the framework
  exits non-zero when a baselined scenario passes, and all four runs exited 0),
  and the release's added tool and fields needed no new entry.

## Catalogue under test

Confirmed against the running build before the suite was invoked:

- Write-enabled: **40** tools advertised, including `refresh_vault`.
- Read-only: **17** tools, matching the golden read-only list. `refresh_vault`
  is correctly **absent**: it is gated on MCP write mode like every other Vault
  control, so the read-only catalogue is unchanged from the 39-tool run.

## Command lines

```bash
npx -y @modelcontextprotocol/conformance@0.2.0-alpha.11 server \
  --url http://127.0.0.1:42999/mcp \
  --expected-failures docs/maintenance/conformance-baseline.yml \
  --requirements 2025-11-25 --output-dir <dir>
npx -y @modelcontextprotocol/conformance@0.2.0-alpha.11 server \
  --url http://127.0.0.1:42999/mcp \
  --expected-failures docs/maintenance/conformance-baseline.yml \
  --requirements 2026-07-28 --output-dir <dir>
```

Run once per write posture (`HATCHDOOR_MCP_WRITE_ENABLED=true|false`, server
restarted between postures via `just dev-start`).

## Pass criteria

All five hold, for both postures:

1. Every invocation exited **0**.
2. Every failure that occurred has a reviewed entry in
   `conformance-baseline.yml`; the summary reports zero unexpected failures.
3. No stale-baseline exit — the baseline needed no amendment this run.
4. All `wire-schema-valid` checks passed in every run; none was baselined, and
   none is baselinable.
5. Evidence archived here: runner version, command lines, summaries, and the
   four results directories.

The failure counts are identical to the superseded run's at each revision, which
is the expected outcome. `refresh_vault` is additive, `get_frontmatter`'s
`content_hash` is an added field on an existing result, and the baseline's
entries are all for capabilities Hatchdoor intentionally does not implement
(prompts, resources, logging, completion, elicitation and sampling) plus the
`tools-call-*` scenarios that call the suite's own reference fixtures. None of
those is touched by this release.

`get_tree` dropping `vault_id` from its notes does not move these numbers
either: the suite validates wire and protocol conformance, not Hatchdoor's own
tool result schemas, and the field's removal is reflected in the tool's
advertised `outputSchema`, which continues to validate.
